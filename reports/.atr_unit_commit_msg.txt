tools: measure the ATR-unit fix (atr_median same-timeframe) - it is a no-op

Adds tools/atr_unit_fix_ab.py and reports/atr_unit_fix_findings.md.

dynamic_levels.py:141-144 compares the timeframe ATR against the registry's
"typical DAILY ATR as % of price", so atr_ratio is pinned at its 0.33 clamp on
68.6% (183d) / 67.1% (365d) of candidate bars. The reported 69.8% is broadly
confirmed; the per-symbol FX range measured here is 63-96%.

Three arms that differ only in how atr_median is derived (A = daily registry,
B = trailing same-TF median, C = daily/sqrt(24)) over 20 symbols, 46,939
(183d) / 94,937 (365d) candidates:

  arm   E[R] 365d   E[R] 183d   median stop (ATR)   trades
  A     -0.05086    -0.11056    2.5756 / 2.5805     46939 / 94937
  B     -0.05088    -0.11062    2.5759 / 2.5810     46939 / 94937
  C     -0.05070    -0.11051    2.5764 / 2.5812     46939 / 94937

The fix changes nothing material: 3 outcome flips in 46,939 trades (0.0064%),
Delta E[R] <= 6e-5 R. The clamp is a red herring because atr_ratio feeds
effective_buffer = max(dynamic_buffer, anti_wick_buffer) and the 0.35*ATR
anti-wick buffer wins in BOTH arms - median effective_buffer is 0.3500 ATR in
every arm. Only 2.41% of bars move the buffer at all (abnormally wide spread),
by at most 0.12 ATR.

Measured directly: the registry's typical_atr_pct is ~3.5x the real H1 ATR
(median ratio 0.288), so the docstring is right and its use is wrong.

Safe to ship as a pure bug fix (behaviourally inert), but it buys nothing: the
"volatility-adaptive buffer" is still not delivered, and atr_ratio is dead code
today. Making the buffer actually adaptive is a separate change needing its own
backtest gate. Read-only with respect to jarvis/.
