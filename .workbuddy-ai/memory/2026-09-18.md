`tests/test_devil_advocate.py` — **150 tests, 58/58 mutations caught**. **No source changes**: every

### 🔴 Dead branch 1 — the liquidity-sweep penalty never fires

The critic tests `sweep_type == "BUY_SIDE"` / `"SELL_SIDE"`. But `LiquidityContext.sweep_type` is only
ever `"BULLISH_SWEEP"` / `"BEARISH_SWEEP"` / `"NONE"` — documented at `schemas.py:94`, produced solely
by `liquidity.py:108,115` (the only other `LiquidityContext` producer, `dynamic_levels.py:561`, leaves
it at the default). Those two strings exist only in `news.py:720`, for an unrelated post-news
narrative. **A fresh sweep against your trade is never penalised.** Intended mapping would be
BUY → `"BEARISH_SWEEP"`, SELL → `"BULLISH_SWEEP"`.

### 🔴 Dead branch 2 — the cross-asset correlation check never fires

It needs a `"EURUSD"`/`"GBPUSD"` key inside `mtf_alignment`, but `market_context.py:115` only ever
writes timeframe keys. `get_correlation` is still called twice per critique (Python evaluates it before
the `and`) and the result discarded. Note the `pair_sym in mtf` guard is *redundant* — removing it
changes nothing, because `isinstance(mtf.get(pair_sym), str)` already no-ops on a missing key.

### 🔴 The HTF conflict message names the wrong frame

`macro_bias = mtf.get("H4") or mtf.get("D1")` prefers H4 whenever it is truthy, so when D1 is the
frame in conflict and H4 is merely NEUTRAL the threat reads "Macro timeframe is NEUTRAL" — naming a
frame that is not in conflict and hiding the bearish one that triggered it. Penalty (12.0) is correct;
only the explanation is wrong.

### Also pinned

  even `"buy "` with a trailing space) is critiqued from the **wrong side**. All four production
  callers pass "BUY"/"SELL" today.
* `critique_confidence` derives only from `context_quality`, so a critic that found eight threats on a

* `SessionContext` defaults to `is_prime_session=False`, so the floor on any default-built context is
  **8.0**, not 0.0.
* Penalty caps at 50.0 against a gate of 43.0 — only **7 points** of range can block, and the largest

## Round 27 — `jarvis/market/market_context.py`: the producer of `MarketContext`

`tests/test_market_context.py` — **89 tests, 47/47 mutations caught**. All five engines are injected
(`MarketContextEngine(structure_engine=…, liquidity_engine=…, …)`), so it is pure and offline — and
that injection is what makes the frame-routing assertions possible: a fake structure engine records
which frame it was handed.

This module is the **only writer of `mtf_alignment`**, so it is the source of both the round-25
defect (SCALP has no H4 key → `structure_analyst` read the absence as divergence) and the round-26
one (the correlation check wanted an "EURUSD" key that is never written). Those were found
downstream; this pins them at the producer.

### Fixed

1. **The DAY_TRADING docstring named the wrong frames.** It claimed "H1 (40%), M15 (35%), M5 (25%)";
   the code weights **H4** 40%, H1 35%, M15 25%, because `df_macro` resolves to the H4 frame for that
   style — and M5 is written into `mtf_alignment` but weighted 0. Docs only; the code was always
   self-consistent.
2. **`test_a_none_context_does_not_raise` was time-of-day dependent.** `master_confluence:138` calls
   `get_active_killzone(getattr(context, "timestamp", None))`; with `context=None` that is `None`, and
   `get_active_killzone(None)` falls back to `datetime.now()`. Identical input scored **4** outside a
   killzone and **14** inside one — the test asserted 4 unconditionally, so it failed for ~8 hours
   every weekday (it passed at 01:14 UTC, failed at 13:44). Fixed with a `frozen_killzone` fixture
   plus a companion test pinning the +10 and naming the wall-clock dependence.

### Pinned, not changed

* **An integer epoch column is silently ignored.** `isinstance(np.int64(0), int)` is **False** —
  numpy ints do not subclass `int` — so `isinstance(raw_ts, (int, float))` at line 104 misses an int64
  time column and the bar time is discarded for wall-clock now. A *float* column works (np.float64
  *does* subclass float) and an object-dtype Python int works; only the ordinary integer column
  breaks. Currently **latent**: every producer calls `pd.to_datetime(…, unit="s")`.
* A **NaN** timestamp *raises* `ValueError` from `datetime.fromtimestamp` (it passes the float check)
  instead of falling back like every other unrecognised type.
* A **string** timestamp silently falls back to now.
* `elif isinstance(raw_ts, pd.Timestamp)` is **dead** — `pd.Timestamp` subclasses `datetime`, so the
  first branch already catches it. Harmless (same behaviour).
* VWAP guards on `volume` and `high` but not `low`, and line 177 reads all three → KeyError.
* VWAP's `isna().all()` only catches the all-NaN case, so one bad bar propagates `nan`.
* An empty `primary` falls back to `list(mtf_data.values())[0]` — caller-order dependent.
* An unknown `trade_style` silently becomes SWING; `trade_style` is returned **uppercased**.
