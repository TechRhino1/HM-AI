**Root cause of the two-line nav — a JS fallback, not a CSS bug.**
`auth.js:137` resolves its host as
`document.querySelector(".nav-links-wrapper") || ".hud-actions" || "header"` and *appends the
account widget into it*. `dashboard.html`, `console.html` and `index.html` declare a real
`#auth-header-widget`; `stocks/india/india_options` did **not**, so four market pills and the
account pill ended up in one flex row whose `flex-wrap: wrap` then broke it.

  `#auth-header-widget` as a **sibling** of the nav, so the widget is never injected inside it.

## Findings to carry forward

* **The 3 pytest failures are weekend-fragile tests, not a regression.**
  `tests/test_market_data_independence.py` — three tests assert `freshness == STALE` after
  `time.time()`-relative epochs, but on Saturday `SessionEngine.get_market_trading_status
  ("XAUUSD")` returns `status=CLOSED_WEEKEND, day_of_week=5, is_open=False`, so the classifier
  correctly answers `MARKET_CLOSED` and the warm-up retry path never runs. Confirmed by querying
  the engine directly. **They should pass again Monday.** Worth fixing so the suite is not
  weekend-red — not done here (out of scope, and it touches the market-data path).
* **`/` serves `dashboard.html`, not `index.html`.** `server.py:381` maps
  `"/", "/index.html", "/dashboard", "/dashboard.html"` → `_serve_dashboard_ui()`; `/classic` →
  `index.html`. Probing "the root page" and expecting the terminal is a trap — the first probe of
  this session did exactly that and reported a missing `.mobile-nav-bar` that was never there.
* **Load order decides which sheet wins, and it differs per page.** The three market pages load
  `page.css` → `auth.css` → `hm_ui.css` (design system last, so it can override), but
  `dashboard.html` loads `hm_ui.css` **first**, then `theme_terminal.css`. Any rule added to
  `hm_ui.css` therefore governs the market pages and does *not* govern the dashboard. Read the
  `<link>` order of the specific page before assuming an override lands.
* **A user's "it's broken" and a measurement disagreeing is itself the finding.** The rail
  *looked* overlapped in a screenshot at 1440 (account pill apparently on top of the session
  badge). Measuring the geometry proved zero overlap at every width — it was the rail's secondary
  band wrapping to a second row, left-aligned. Do not "fix" a layout defect that a bounding-box
  comparison cannot reproduce.

# Part 2 — navigation drawer (`50744c3`, pushed, remote == local)

The user said "continue" without answering the scoping questions, so I took the safest
defensible reading of each remaining ask and implemented the one with the best
value-to-risk ratio: **grouped navigation** ("group related buttons", "rebuild the navigation
bar", "side bars") as an off-canvas glass drawer on the terminal, below 768px.

## Design decision worth keeping: build on the controller that is already there

`dashboard.js` already has a generic dropdown controller keyed on
`[data-dropdown-trigger]` + `aria-controls` → `[data-dropdown-panel]`, giving toggle, Escape and
click-outside for free. It also wires every `[data-view-btn]` / `[data-pane-btn]` by delegation,
and `setView`/`setPane` sync `aria-selected` across *all* elements carrying those attributes.

So the drawer is markup + CSS only, plus **12 lines of JS**. There is no second source of truth
for the active view, and no parallel open/close state to fall out of sync. The 12 lines exist
because the dropdown controller deliberately *ignores* clicks inside a panel (correct for a
menu, wrong for a navigation drawer); that handler is scoped to the drawer element so no
existing dropdown changed.

The Panels section is revealed from `body[data-view]` — state `setView` already maintains —
so the drawer cannot offer a control that would do nothing outside the Trade view.

## The defect that only measurement caught

The drawer carries the **`data-dropdown-panel` attribute** (what the JS reads) but not the
**`.tt-dropdown__panel` class** (what the CSS targets). It therefore inherited *none* of that
rule's properties — including `z-index`. The drawer computed to `z-index: auto` while the scrim
is explicitly at `--hm-z-drawer - 1`, so **the scrim painted over the top of the drawer**. It
opened, closed, switched views, moved focus and passed every functional assertion while being
dimmed to unreadability. The screenshot looked merely "murky"; only
`elementFromPoint(drawer centre)` returning `nav-drawer-scrim` made it unambiguous.

Two generalisations, both now in `TRAPS.md`:
* A `data-*` attribute and a class of the same name are different contracts. Check which one
  the CSS actually targets before assuming a component inherits a rule.
* **Assert paint order, not just behaviour.** `getComputedStyle().zIndex` and
  `elementFromPoint()` catch "renders underneath its own backdrop", which no functional
  assertion or contrast check will.

Also fixed: the drawer's active item was unhighlighted on first load, because `setView` only
syncs `aria-selected` *after* a click. The markup now mirrors the inline controls' initial
state (`aria-selected="true"` on Trade and Watchlist).

## The /classic chart header could not fit, and could not yield

`.chart-header-bar` is a nowrap flex row whose two children (`.chart-symbol-info` 559px,
`.chart-controls-group` 493px) were **both `flex-shrink: 0`**. It needs ~1071px. Measured
consequences, all of which were present in the shipped tree:

| viewport | chart panel | header needs | what was lost |
|---|---|---|---|
| 1440 | 786px | 1071px | the **whole M1..D1 row**, `Levels: ON`, `Expand` |
| 1024 | 488px | 1071px | `Expand` (and Levels at 901) |
| 901  | 365px | 1071px | `Levels: ON`, `Expand` |
| 390  | 374px | ~990px  | everything after the engine switcher, at x=777..1014 |
| 360  | 344px | pill alone is 340px in a 326px strip | 14px header overflow |

They were in the DOM the whole time. `.terminal-panel` is `overflow: hidden`, so they were
**clipped, not cramped** — and `tools/verify_ui_layout.js` does not cover `/classic`, so nothing
in the repo could see it.

The desktop clipping is **pre-existing**, not caused by this round's work: the probe measures the
live header, `unwrap()`s the disclosure panel in the DOM, measures again, and gets byte-identical
control geometry and identical overflow both ways.

Four fixes, one per constraint: the header bar wraps; the symbol strip may shrink and wrap
(`min-width: 0` lifts the automatic min-content floor that pinned it at the pill's 340px); the
controls group may shrink and wrap; the market-status pill may wrap on a phone. Below 901px the
secondary controls collapse behind a "Chart" disclosure that reuses the existing inline handlers.

## A real, user-visible encoding bug

Five lines of `terminal.js` were CP1252 double-encoded (UTF-8 -> CP1252 -> UTF-8). The one that
mattered: pressing **Expand** rewrote the button as `â›¶ Expand`. Also the crosshair tooltip's
`⚠` / `✓` / `✦` tags and the file-header comment.

Nothing raises for this class of corruption — the mojibake is still a valid string — so it is
invisible to any substring assertion. `tools/audit_encoding.py` reports and repairs it (the whole
tree is now clean, 689 files); `tests/test_encoding_integrity.py` (19 tests) fails the build if it
returns. Two of those tests pin behaviour a naive fixer gets wrong, both hit while writing it:

* a run is only corruption when it re-encodes to CP1252 **and** decodes as UTF-8;
* **line endings must survive a repair** — the first version rewrote all 3429 CRLF endings of
  `terminal.js` because text-mode `open()` translates newlines unless you pass `newline=""`.
