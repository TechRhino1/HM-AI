# Part 2 — navigation drawer (`50744c3`, pushed, remote == local)

The user said "continue" without answering the scoping questions, so I took the safest
defensible reading of each remaining ask and implemented the one with the best
value-to-risk ratio: **grouped navigation** ("group related buttons", "rebuild the navigation
bar", "side bars") as an off-canvas glass drawer on the terminal, below 768px.

## Design decision worth keeping: build on the controller that is already there

`dashboard.js` already has a generic dropdown controller keyed on
`[data-dropdown-trigger]` + `aria-controls` → `[data-dropdown-panel]`, giving toggle, Escape and
click-outside for free. It also wires every `[data-view-btn]` / `[data-pane-btn]` by delegation,
and `setView`/`setPane` sync `aria-selected` across *all* elements carrying those attributes.

So the drawer is markup + CSS only, plus **12 lines of JS**. There is no second source of truth
for the active view, and no parallel open/close state to fall out of sync. The 12 lines exist
because the dropdown controller deliberately *ignores* clicks inside a panel (correct for a
menu, wrong for a navigation drawer); that handler is scoped to the drawer element so no
existing dropdown changed.

The Panels section is revealed from `body[data-view]` — state `setView` already maintains —
so the drawer cannot offer a control that would do nothing outside the Trade view.

## The defect that only measurement caught

The drawer carries the **`data-dropdown-panel` attribute** (what the JS reads) but not the
**`.tt-dropdown__panel` class** (what the CSS targets). It therefore inherited *none* of that
rule's properties — including `z-index`. The drawer computed to `z-index: auto` while the scrim
is explicitly at `--hm-z-drawer - 1`, so **the scrim painted over the top of the drawer**. It
opened, closed, switched views, moved focus and passed every functional assertion while being
dimmed to unreadability. The screenshot looked merely "murky"; only
`elementFromPoint(drawer centre)` returning `nav-drawer-scrim` made it unambiguous.

Two generalisations, both now in `TRAPS.md`:
* A `data-*` attribute and a class of the same name are different contracts. Check which one
  the CSS actually targets before assuming a component inherits a rule.
* **Assert paint order, not just behaviour.** `getComputedStyle().zIndex` and
  `elementFromPoint()` catch "renders underneath its own backdrop", which no functional
  assertion or contrast check will.

Also fixed: the drawer's active item was unhighlighted on first load, because `setView` only
syncs `aria-selected` *after* a click. The markup now mirrors the inline controls' initial
state (`aria-selected="true"` on Trade and Watchlist).

## Correction to my own earlier reporting: the drawdown guard is NOT inert

I have been reporting each round that `daily_start_equity = 777.0` made the daily-loss cap
"inert". That was **backwards**. `DrawdownGuard._load_state()` compares the saved date and zeroes
`daily_start_equity` on a new day, and `update_equity_benchmarks()` re-anchors it to the current
equity — so the 4% daily cap is correctly armed from today's 777. The daily cap was never the
problem.

**`peak_equity` is the problem, and it is the opposite failure: it is permanently tripped.**
`peak_equity` moves **up only** (line 171) and is **never** reset on a new day. It sits at
`10150.0`, so:

```
total_dd_pct = (10150 - 777) / 10150 * 100 = 92.34%   >=  max_total_drawdown_pct = 10.0
```

`check_limits()` -> `passed=False`; `get_risk_multiplier()` -> **0.0**. Three call sites refuse:
`risk_engine.py:201` (adaptive gate 10), `:405` (`authorized: False, lots: 0.0`), and
`orchestrator.py:551` (backstop that flips EXECUTE to WAIT with
`DRAWDOWN_GUARD: Max Portfolio Drawdown breached`). **The live engine will refuse every trade.**

## Root cause: paper and live share one drawdown state file

`RiskEngine` builds the guard as `DrawdownGuard(..., db_path="" if is_backtest else
"jarvis_drawdown_state.db")` — so **paper mode and live mode write the same file**. Paper mode
reports `balance=10000.0, equity=10000.0 + paper_pnl` (`mt5_client.py:179`), so a paper session
that reached +150 pinned `peak_equity = 10150`, and that value now blocks the live account. The
paper peak is indistinguishable from a real one to the guard.

Fix is two parts and they are separable: (1) re-anchor the live baseline via the documented
`reset_baselines()`; (2) give paper its own db so it can never poison live again. Part (2) is the
real fix; part (1) is the operator action the module docstring says only an operator may take.

## Second defect: `config/settings.json`'s whole `risk` block is dead configuration

`jarvis/config/settings.py:86-105` carefully loads `risk.*` into `cfg.risk` — and **nothing ever
reads `cfg.risk`**. The only two references in the tree are the two writes inside `settings.py`
itself. `RiskEngine()` is constructed with **no arguments** (`orchestrator.py:98`), so its
hardcoded defaults win:

| key | settings.json | RiskEngine default | direction |
|---|---|---|---|
| `max_daily_loss_pct` | 5.0 | 4.0 | engine stricter (safe) |
| `max_open_positions` | 2 | **3** | **engine looser** |
| `max_symbol_expositions` | `max_symbol_exposure_count: 1` | **2** | **engine looser** |
| `max_risk_per_trade_pct` | 0.5 | 0.5 | equal, masks the gap |

The two that differ in the *looser* direction are concurrent-position limits. Editing
`settings.json` has no effect on any of them.

## Operational note

The platform is running only as a session background task — it dies when the session does.
`HM_start.py` must be run in the user's own terminal window to persist. Also, `HM_start.py` has
**no confirmation gate**: `live` is the default and it goes straight to an autonomous engine.

**The real defect.** The dashboard rail: **4 bands / 229px at 360px**, 27% of an 844px screen, sticky.
