### The audit

Four agents ran in parallel with bounded charters (architect / data / AI / Python), each required to
cite `file:line` or a measurement, each told to separate real defects from deliberate design.
Findings IDs: A1–A17, D1–D17, AI1–AI16, P1–P17.

Headline structural problems:
1. **Money path can fail silently and permanently** — P1: `timeout_guard.py:37-47`,
   `future.result(timeout=)` never cancels and `_get_executor` only rebuilds on `_shutdown`, which
   never flips. 16 hung broker calls ⇒ every later call returns its default forever, **including
   the calls that close positions**.
2. **The configured risk limit is not enforced** — `position_sizing.py:86-89` clamps to a hardcoded
   literal `1.50` vs configured `max_risk_per_trade_pct = 0.5`, then multiplies by two more factors
   *outside* the clamp (C1, carried from the trade audit).
3. **>50% of trade history is fabricated** (C2/D1/D2/D5) and still being written today.
4. **The learning loop reads its own output** — `expected_value` is overwritten with realised P&L on
   close (111/111), and `triple_barrier_label`/`mfe`/`mae` are 0 on 35/35 rows (AI2/AI3/AI5).

## Round 40c — D2: trades could never close (M1 complete)

  `result.order` (the ORDER ticket) and `log_trade` stored it; `sync_mt5_history` closes rows with

  `log_trade` callers (`execution_engine.py:149`, `server.py:1033`) persist it; the join is now
  `position_id = ? OR (position_id IS NULL AND ticket = ?)` so pre-column rows still close, and the

* **Proven pre-fix:** the sync INSERTED a duplicate row instead of closing the original
  (`tests/test_position_id_join.py`, 4 tests).
* Naming trap: the order-sending method is **`send_market_order`**, not `place_market_order` — the

## Round 40d — the suite became uncollectable (environmental, pre-existing)

* **P5 escalated, with a measurement.** `jarvis/api/server.py:34` builds `MT5Client(mode="live")`
  in the **class body**, so importing the module initialises MT5. With no terminal running,
  `mt5.initialize()` blocks in a native call **holding the GIL**; `Thread.start()` then can never
  complete, so `import jarvis.api.server` never returns and **pytest cannot even collect** (observed
  13min+ with zero output; `faulthandler` showed the worker at `mt5_client.py:62` and the main
  thread at `threading.Thread.start`). `TimeoutGuard` cannot help — a timeout cannot interrupt a
  thread, and no new thread can be created while the GIL is held. This is why the suite that ran in
  2min at 22:19 hung at 04:33: the MT5 terminal had gone away (no `terminal.exe` running).
* **Verification workaround:** `.scratch/nomt5/MetaTrader5.py` — a stub that answers "no terminal"
  instead of deadlocking. `PYTHONPATH=.scratch/nomt5 pytest tests` then completes
  (**2550 tests, 5 failures**: the 3 weekend-only `test_market_data_independence` ones, plus 2 that
  genuinely need a live terminal — `test_backtest_with_historical_engine` needs real history and
  `test_candle_freshness` asserts a LIVE_MT5 stamp). Neither is a regression.
* Also fixed while doing D2: I had put `CREATE INDEX ... position_id` **before** the `ALTER TABLE`
  migration block, so on an existing DB the index raised, `_init_db` aborted, and the column was
  never added ("Failed to initialize SQLite DB: no such column: position_id"). Indices on new
  columns must come after the migration — the whole block is one try/except.
* Escape hatch that already exists: `JARVIS_BACKTEST_MODE=1` makes `init_connection` skip
  `mt5.initialize()` entirely.

## Round 40f — M2 begins: D3 schema version stamp

* **All 11 databases reported `user_version = 0`** — no file could declare its own shape, and two
  copies of `jarvis_history.db` (root and `data/`) have already drifted (root has no `closed_at`).
* New `jarvis/data/schema_version.py`: `read_version` / `write_version` / `ensure_version`.
  All five stores now stamp themselves at version 1 — `SQLiteTradeDB` (executed_trades),
  `TradeMemory` (trade_records), `MetadataDB`, `CircuitBreaker`, `DrawdownGuard`.
* **The drift rule is the point:** a file written by NEWER code is *not* stamped down. Stamping it
  down to what this version knows is exactly how columns get silently dropped. It is left alone,
  logged at ERROR, and the caller is told the real number. Version 0 means "predates versioning"
  and is treated as current, since every existing file is 0.

### The mechanism

|---|---|---|---|---|---|

* `dynamic_levels.calculate_levels` — refuses to **mint**: returns a HOLD-shaped result with the same

* `decision_engine._compute_bias_and_levels` — refuses to emit a **direction**. `decision_action`
  becomes EXECUTE on `gate_passed and bias in (BUY, SELL)`, so a BUY/SELL beside a zero entry would
  have been marked executable. Returns `("HOLD", 0.0, …, None, 0.0)` — same 8-tuple arity.
* `trade_guard.validate_pre_execution` — refuses to **authorize**: the finiteness loop now also
  requires a positive price, catching any other `DecisionObject` producer.
* `tradingview_provider.fetch_candles` — returns `None` when the anchor quote is a fallback. The series
  is anchored to it bar by bar (including the "genuine live OHLCV" last bar), and
  `fetch_real_candles` logs whatever comes back as "Live TradingView candles". Refusing lets the tier
  hierarchy reach Tier 4, which labels itself. Also tightened `price <= 0.0` → `is_observed_price`,

## Round 40q — D10 the triple-barrier label; D19 opened for MFE/MAE (M2)

### The measurement that framed it
`triple_barrier_label` was **0 on 36/36 rows** (`data/jarvis_trade_memory.db`), one distinct value,

### The fix
`derive_triple_barrier_label(entry, exit_price, sl, tp, trade_type)` in `trade_memory.py` — a pure
function, derived at **close** from the row's own stored geometry:
+1 reached the take-profit barrier, −1 reached the stop, 0 stopped between them (vertical barrier),
and **`None` when the row cannot answer**, so "unlabelled" stays distinguishable from "vertical
barrier hit". `COALESCE(?, triple_barrier_label)` in the UPDATE means an explicit caller-supplied
label is never downgraded to NULL. `record_trade` no longer invents one at open.

**Projected over the live journal: 5 × −1, 1 × +1, 16 × 0, 14 × unlabelled** (the unclosed rows).
All six non-zero labels agree in sign with the realised `pnl` — an independent check.

### Two traps found while building it
* **A float artifact was deciding the label.** Live row `938435830` stored
  `sl = 111.29999999999998` and filled at `111.30`, so a plain `exit <= sl` answered "**not
  reached**" for a trade that *was* stopped out — the label would be set by float noise rather than
  by the market. Added a **relative 1e-9 tolerance**, far below one tick (a BTCUSD tick is ~1.2e-7
  relative, a EURUSD pip ~8.7e-6), so it cannot swallow a genuine near-miss.
* **"Both barriers hit" is not a gap — it is contradictory barriers.** For a well-formed BUY,
  `exit >= tp` and `exit <= sl` cannot both hold: a gap fills *on or beyond* whichever barrier was
  touched, which classifies cleanly. So the condition means `tp <= sl`, i.e. the row is malformed.
  **My first version guessed `-1` there** and I wrote a test asserting the wrong premise
  (`exit=200, sl=99, tp=101` → only the TP condition is true, so it returned `+1`). It now refuses
  (`None`). Two of my test cases also assumed a single `sl/tp` pair works for both sides — it does

## Round 40r — D3 remainder: `trade_records` onto `migrate()` (M2)

### The sweep, and why it mattered
`TradeMemory._init_db` ran this on **every open**:

```python
cur.execute("PRAGMA table_info(trade_records)")
columns = [info[1] for info in cur.fetchall()]
if 'ml_features' not in columns:
    cur.execute("ALTER TABLE trade_records ADD COLUMN ml_features TEXT")
if 'triple_barrier_label' not in columns:
    cur.execute("ALTER TABLE trade_records ADD COLUMN triple_barrier_label INTEGER DEFAULT 0")
```

It ignores `user_version` entirely, so it cannot express ordering, a backfill, or a refusal. The
refusal is the part that bites: handed a file from **newer** code that no longer carries
`triple_barrier_label` (renamed or dropped), the sweep **re-adds it**, silently undoing the newer
schema — while `ensure_version` logs "written by newer code" about a change the sweep has already
made. Replaced with `migrate()` + `MIGRATIONS = {1: _migration_1}`, so the step runs at most once
and a newer file is refused rather than patched back.

### A second, independent defect found while testing it
`record_trade` used `INSERT OR REPLACE INTO trade_records VALUES (?, … ×22)` — **22 bare
placeholders, no column names** — so it is pinned to this version's exact column count and fails
outright against a 23-column file: `table trade_records has 23 columns but 22 values were supplied`.
That is precisely what a file written by newer code looks like, so the store could correctly decide
to open a newer file and still be unable to write to it. The insert now names its columns, which
tolerates extra ones and is immune to reordering. Found because a test asserted "refusing to migrate
is not refusing to operate" and the write blew up.

### Mutation proof: only 2 of 8 go red — and that is the real measurement
`.scratch/revert_d3_fixes.py` restores the sweep and the positional insert. RED:
`test_a_newer_file_is_not_patched_back_into_this_schema` and
`test_a_newer_file_with_an_extra_column_is_still_writable`. The other **6 pass under both
implementations**, because the sweep happens to be correct for them: it does add missing columns,
is idempotent on re-open, and (via `ensure_version`) does refuse to stamp a number down.

**So the honest measure of what `migrate()` bought here is the refusal, not the mechanics.** Worth
saying plainly rather than counting 8 tests as "coverage".

### Retraction carried over
The 40q note claiming "the paper-scoped store is not stamped" was **wrong** and has been corrected in
place. Constructing a `DrawdownGuard` on a paper-scoped path stamps it `uv=1` immediately; the file
just was not reopened after the stamping landed (mtime 03:42 vs 14:09 for the live sibling). The
trap version is now recorded in `TRAPS.md` § 40q.

### Evidence
`tests/test_trade_memory_migration.py` (8 tests): the step exists for the version it names; a legacy
`uv=0` file gains both columns and is stamped 1; a brand-new file is versioned without a phantom
migration; opening twice does not reapply the step; a current file is left alone; a newer file is
neither patched back nor stamped down; and a newer file with an extra column is still writable.

## Round 40t — D19 shipped: `mfe` / `mae` are measured now, or NULL

Measured on the live journal first: **36/36 rows at `mfe = 0.0`, 0 NULLs** — every trade in

### The root cause was a deletion, not the hardcoded literal
`orchestrator.py` passing `mfe=0.0, mae=0.0` was the symptom. `PositionMonitorEngine` already tracked a

## Round 40u — A10's SSE half: the stream now pushes a digest

Measured rather than cited. `/api/telemetry_state` returned **63,276 bytes** (15 radar rows, 5
decisions). `/api/stream/telemetry` re-sent all of it on every state-version change, up to once a
second → **61.8 KB/s per client**; the reported 144 KB/s is two or three dashboards open at once.

### What did NOT work, and is worth remembering
My first design was a generic per-field byte budget: elide any value whose serialisation exceeds N.
Measured against the real payload it saved almost nothing — **94% of the original at a 256-byte
threshold, 84% at 64**. Reason: the 2.6 KB per radar row is spread across ~34 fields of ~77 bytes each.
No field dominates, so truncating values cannot help. What was needed was dropping **fields**.

Final: a named denylist of explainability keys (`checks`, `rejection_reasons`, `failing_reasons`,

* **Denylist, not allowlist** — a new *small* field passes through automatically, so the digest cannot

* **`/api/telemetry_state` untouched.** dashboard.js, console.js and terminal.js all read

* **`latest_decisions` capped in the digest only, never evicted from the store.** `copilot.py:485,507`

## Round 40v — P3: the last open P0 item, and the specified fix was wrong

### First: the P0 table was stale
Five rows (C1, D4, D2, A3, P2) were marked open but are all done per the M1 table ("6 of 6"). Updated
them. The P0 table is the front page of the plan; leaving it stale is its own defect.

### P3 is real — measured
`MT5Client._shared_lock` is a **class** attribute shared by every instance, held ACROSS native broker
calls. `.scratch/repro_p3_lock.py`: wedge one worker and **5/5 later workers block to their full
timeout**, each surfacing as its own anonymous "Timeout" default. The platform goes dead while looking
merely slow.

### But the stated fix would have been a mistake
P3 said *"stop holding a global lock across the broker call"*. Two reasons not to:
* The lock serialises calls into the MetaTrader5 Python bindings, which are **not thread-safe**.
  Removing it trades an availability bug for a correctness one.
* You cannot abandon the lock when a call hangs: `TimeoutGuard` bounds the **caller**, but the worker
  it leaves behind is still inside a native call holding the lock, and **Python cannot kill a thread
  blocked in C**.

So the fixable part is what made it *invisible*:
* `jarvis/execution/broker_lock.py` — `TrackedRLock`, a drop-in `RLock` (so `with self._lock:` still
  works and **zero call sites changed**) that bounds the wait and records the holder — thread, task,
  age. A starved waiter raises `BrokerLockBusy` naming them.
* `MT5Client.broker_lock_health()`, to be reported alongside `TimeoutGuard.health()`.

Two deliberate constraints: the timeout applies to **acquiring only**, never to holding, so a
slow-but-progressing call is untouched; and `DEFAULT_WAIT_SEC = 10` is longer than any broker timeout,
so the lock never becomes the thing that fails a call.

**Residual, stated in the plan:** a stuck native call still disables the broker until restart. Once a
thread is lost inside MetaTrader5 the connection is suspect; the honest goal is to detect and report,
not to pretend to recover. Full recovery needs broker calls on a single owning thread (an actor) — not
done here.

### Mutation: two, because the change has two halves
* revert the client to a plain `RLock` → **2 red** (the wiring)
* make the wait unbounded again → **5 red** (the behaviour)

7 distinct tests discriminate it. Reporting only one number would have misrepresented either half.

Suite **2854 passed / 0 failed**. `MEMORY.md` 6,557 → 6,517 after five more trims.

## Round 40x — AI6: the learning loop survives a restart (committed `cb8e581`)

### The defect, one root and two consequences
`JarvisOrchestrator._pending_features` is a plain dict holding direction, entry, stop, symbol,
strategy, regime and the feature vector — everything `_on_trade_closed` needs.

1. **Learning died on every restart.** A trade opened before this process arrived with
   `pending is None`, so the ML and bandit updates were skipped — although `record_trade` had
   already persisted all of it to `trade_records`.
2. **R was invented from the outcome flag:** `r_multiple = 2.0 if is_win else -1.0`.

### The consumers could not refuse it
* `strategy_bandit.py:159` — `float(r_multiple or 1.0)` turned an explicit `None` into **+1R**,
  and also collapsed an honest `0.0` into +1R (classic falsy-zero bug).
* `ensemble_bandit.py` — `max(0.5, None)` raised **TypeError** outright.

### Fix: recover, don't guess
`TradeMemory.fetch_trade(ticket)` + `JarvisOrchestrator._recover_pending_features(ticket)` rebuild
the open-time context from the journal. Three details that matter more than the recovery itself:
* **`risk_dist` is 0.0 when the stop was never stored** — `|entry - 0|` is not a risk distance; on
  EURUSD it reads as 11,000 pips.
* **An absent feature vector stays absent** — `record_trade` json-dumps `[]` when none was given,
  and a gradient step on an all-zero vector is a fabricated observation.
* R is `None` when not derivable and stays `None`.

### The decision I had to make (the reusable part)
The two consumers take the same unknown R and must be treated **differently**:
* **To the bandit, `rewards` is a RECORDED quantity denominated in R** → unknown R *withholds* it.
  But the win/loss IS measured, so the trade is still recorded and `pulls`/Beta still move.
* **To `update_online`, R is only the WEIGHT on the gradient** — a hyperparameter nothing later
  reads as "this trade made 1R" — while the label being learned (`is_win`) is measured regardless.
  So the update still runs and the argument is **omitted**, letting the declared default apply.
  Passing `None` would be coerced and indistinguishable from a measured +1R.

**Rule: a recorded quantity is withheld when unknown; a hyperparameter takes its default.**
I first got this wrong by skipping the ML update entirely; suite caught it
(`test_d1_online_ml_and_trade_memory_learning_loop`, 197 != 198) — the D1 test's fixture had only
`features`, no geometry. I did **not** weaken that test; I corrected my fix instead.

### Proof
`tests/test_learning_survives_restart.py` (28 tests). `.scratch/mutate_ai6.py apply|restore` —
a source-level mutation with backup, because four of the changes are inline and cannot be
monkeypatched. **19 of 28 go red.** The 9 survivors pin contracts the mutation does not move
(unknown ticket → None, a loss still costing −0.5, a measured R still credited, and the neutral
one-win increment, which is 1.0 either way and therefore cannot discriminate).

Suite **2894 passed / 0 failed** (was 2866; the 3 weekend-only failures pass today).

### Mutation-harness trap
My first `fetch_trade` mutation changed `WHERE ticket = ?` → `WHERE ticket = -1` while still
supplying a binding → `ProgrammingError`, which the orchestrator's `except Exception` swallowed
into `pending = None`, conflating two mutations and producing two bogus reds. A mutation must
reproduce the OLD BEHAVIOUR, not just break: use `WHERE ticket = ? AND 1 = 0`.

2. **Any bin with 2 observations moved 60% of the way to the observed rate.** Bins held 3–5 rows
   (SE 0.18–0.27); at n=2 the rate can only be 0.0 / 0.5 / 1.0.
3. **The result could be non-monotonic.**

### Measured effect of a single refit

| bin | before | after |
|---|---|---|
| (0.5,0.6) | 0.590 | **0.236** |
| (0.6,0.7) | 0.660 | **0.414** |
| (0.7,0.8) | 0.740 | **0.496** |
| (0.8,0.9) | 0.820 | **0.448** |
| (0.9,1.0) | 0.860 | **0.464** |

A raw 0.60 mapped to **0.325** instead of 0.625 → the 55% gate became unreachable. And the curve
came out **inverted**: 0.75 → 0.496 but 0.95 → 0.464, so a more confident forecast scored lower —
inverting ranking, making the gate reward the worse trade.

### Fix
`DecisionObject.raw_win_prob` (pre-calibration hypothesis probability), threaded out of
`_compute_blended_probability`, persisted via **migration 2**; rows without it are **skipped, not
defaulted**. Refit needs 10/bin, shrinks with a Beta prior `(n·obs + k·prior)/(n+k)`, k=10, then
`_enforce_monotonic`.

`tests/test_calibration_refit.py` (17 tests), **11 red** under `.scratch/mutate_ai10.py`.

### The trap worth remembering: a hardcoded "newer version"

`tests/test_trade_memory_migration.py` used a literal `version=2` to mean "newer than the code".
Bumping `SCHEMA_VERSION` to 2 silently turned **two refusal tests into current-version cases that
passed without testing anything**. Now `NEWER_VERSION = SCHEMA_VERSION + 1`.
**Any test that hardcodes a version/sequence number becomes vacuous the moment the number moves.**
