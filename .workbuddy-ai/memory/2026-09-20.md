# 2026-09-20

## Round 40 — end-to-end audit by four specialist agents; master plan; first implementation

Deliverables at repo root: **`MASTER_PLAN.md`** (ranked backlog + milestones M0–M5) and
**`AGENT_SYSTEM.md`** (the multi-agent coding system: roster, 6-phase workflow, Definition of Done).

### The audit

Four agents ran in parallel with bounded charters (architect / data / AI / Python), each required to
cite `file:line` or a measurement, each told to separate real defects from deliberate design.
Findings IDs: A1–A17, D1–D17, AI1–AI16, P1–P17.

Headline structural problems:
1. **Money path can fail silently and permanently** — P1: `timeout_guard.py:37-47`,
   `future.result(timeout=)` never cancels and `_get_executor` only rebuilds on `_shutdown`, which
   never flips. 16 hung broker calls ⇒ every later call returns its default forever, **including
   the calls that close positions**.
2. **The configured risk limit is not enforced** — `position_sizing.py:86-89` clamps to a hardcoded
   literal `1.50` vs configured `max_risk_per_trade_pct = 0.5`, then multiplies by two more factors
   *outside* the clamp (C1, carried from the trade audit).
3. **>50% of trade history is fabricated** (C2/D1/D2/D5) and still being written today.
4. **The learning loop reads its own output** — `expected_value` is overwritten with realised P&L on
   close (111/111), and `triple_barrier_label`/`mfe`/`mae` are 0 on 35/35 rows (AI2/AI3/AI5).

### Implemented (M0)

* **P1** `timeout_guard.py` — per-pool `_jarvis_stuck` counter, released via `add_done_callback`
  when an abandoned call finally returns; pool replaced once no workers are free; `health()`
  exposes `stuck_workers`/`wedged`. Regression tests in `tests/test_timeout_guard.py`.
  **Proved the wedge**: with pre-fix logic restored, new work returns `FALLBACK`; post-fix `OK`.
* **P4** `orchestrator.py:586` — the guard read `_execution_in_progress` then released the lock and
  claimed 90 lines later (TOCTOU ⇒ duplicate orders). Now an atomic compare-and-claim; the loser
  releases its risk reservation and skips.
* **P9** `order_manager.py` — `_initial_sl`/`_exit_policy` check-then-set ran on the 32-thread sweep
  pool unguarded; added `_state_lock` (RLock) around the freeze, the read, and `forget_ticket`.
* **P7** `position_monitor.py:990` — read `state_manager._decisions`; the real attribute is
  `latest_decisions` (`state_manager.py:40`). The AttributeError was swallowed by `except: pass`,
  so the cached-regime branch had **never executed**. Fixed the name and made the handler log.

### M1 — 4 of 6 done (second pass)

* **C1** `position_sizing.py` — now clamps `effective_risk_pct` to the configured
  `max_risk_per_trade_pct` with the multipliers applied *inside* the clamp. Verified: worst-case
  multipliers (conviction 1.35 × evidence 1.15) produce exactly **0.500%** ($50.00 on $10k) where
  the old formula gave **0.776%** ($77.62 = 1.55x the limit). New test
  `tests/test_risk_ceiling_enforced.py`.
* **D4** `trade_memory.py` — `TradeMemory` now checkpoints `wal_checkpoint(TRUNCATE)` after every
  write and before close. Pre-fix proof is stronger than reported: a copy of the `.db` alone did
  not even contain the `trade_records` **table** — schema *and* rows were trapped in a 16KB WAL.
  New test `tests/test_trade_memory_wal.py`.
* **A3** `orchestrator.py` — `__init__` defaults to `SETTINGS.trading.symbols` instead of 13
  hardcoded symbols. **⚠ Behaviour change: effective universe 13 → 5** (XAUUSD, EURUSD, GBPUSD,
  USDJPY, BTCUSD). Logs a warning listing both sets. New test `tests/test_symbol_universe_wiring.py`.
* **P2** — `place_market_order` timeout returns **`UNKNOWN`**, not `FAILED`; orchestrator holds the
  risk reservation and starts the cooldown (instead of releasing + retrying, which could double a
  position); `dashboard.js` `ACTION_REFUSED` gains `UNKNOWN` so an unconfirmed order can never
  render as a filled trade; contract test gains an `INDETERMINATE` class + a test that it is never
  a completion and always covered by the UI refusal set.

**C2 deferred (documented in MASTER_PLAN.md).** The provider already tags `is_fallback: True`, but
only ONE consumer checks it (`mt5_client.py:311`). Trade prices reach the journal via
`execution_engine.py:92` `fill_price = res.get("price", decision.entry_price)` — so the ongoing
fabricated rows originate in the *decision engine's* price, not the provider fallback. Deleting the
fallback would also break stocks/india display, which legitimately need a reference price.

### Traps learned

* **Verify an agent's highest-impact claim before planning it.** The single most valuable step: the
  AI agent's top recommendation was confidently wrong and would have caused active harm.
* **A trained-but-unloaded model may be a decision, not a bug.** Read the docstring next to the load.
* **A test that cannot fail proves nothing.** Reproduce the defect with the fix reverted.
* `except: pass` can hide a typo for the entire life of a feature (P7).

## Round 40b — C1 unblocked, test isolation, commit

* **C1 now ships.** It had been reverted earlier because the suite went red. The cause was NOT the
  clamp — it was a test-isolation leak, and bisecting the *test order* (not the code) found it in
  under 10 minutes: `tests/test_action_response_contract.py` (alphabetically first) is enough to
  break `test_d1_online_ml_and_trade_memory_learning_loop`.
* **New finding A18 (found while implementing, in no agent report): paper mode sizes against the
  live broker balance.** `get_account_snapshot()` queries `mt5.account_info()` *before* checking
  `self.mode` (`mt5_client.py:150-169`), so a connected paper client returns the REAL account —
  measured **762.51** where a test had mocked 10,000. `MT5StateSynchronizer` (`state_synchronizer.py:56`)
  caches it into `state_manager.account`, and `run_cycle_for_symbol` prefers that over
  `mt5_client.get_account_snapshot()` — so a mock installed *after* construction is dead.
  Consequence: test outcomes depended on test ordering and on the size of a real demo account.
* Why C1 exposed it: at 0.01 lots XAUUSD risks 1.31% of $762.51. The micro-account floor allows the
  minimum lot while forced risk <= 2x the target — 2 x 0.776% (old, inflated) = 1.55% → allowed;
  2 x 0.575% (new, honest) = 1.15% → refused. The test had been passing by arithmetic accident.
  Fixed by pinning `orch.state_manager.update_account(snapshot)` in `test_d1`.
* **C1 verified pre-fix → post-fix:** worst case $70.00 → $50.00 on $10k (1.40% → exactly 0.500%).
  `@unittest.expectedFailure` removed from `tests/test_risk_ceiling_enforced.py`.
* Removed the `JARVIS_TM_NO_CHECKPOINT` bisect switch from `trade_memory.py`.
* **Suite: 2546 tests, 3 failures** — the known weekend-only `test_market_data_independence` trio.

### Traps learned (round 40b)

* **`res.get("execution", {})` returns `None`, not `{}`, when the key exists with value `None`.**
  The `AttributeError: 'NoneType' object has no attribute 'get'` pointed at `res` and sent me
  chasing a function that provably cannot return `None`. Read the default's semantics first.
* **Bisect the test *order*, not just the code.** `pytest <prefix files...> <target test>` with a
  binary search over the alphabetically-sorted file list localises cross-test pollution fast.
* **A test that only passes because a clamp is loose is a latent failure, not a passing test.**
  Tightening a limit is a legitimate way to discover it — do not assume the new code is at fault.

## Round 40c — D2: trades could never close (M1 complete)

* **D2 — the journal join used the wrong MT5 identifier.** `send_market_order` returned
  `result.order` (the ORDER ticket) and `log_trade` stored it; `sync_mt5_history` closes rows with
  `WHERE ticket = deal.position_id` (the POSITION id). Different numbers, so an entry row could
  never be matched to its exit deal. Measured on `jarvis_history.db`: **155 rows** with `closed_at`
  NULL and `realized_pnl` 0.0 (the plan's 212 was from an earlier snapshot).
* Fix: `executed_trades.position_id` added via the existing `ALTER TABLE` map in `_init_db` (no new
  migration machinery needed); `send_market_order` resolves it from the deal
  (`history_deals_get(ticket=result.deal).position_id`, falling back to `positions_get`); both
  `log_trade` callers (`execution_engine.py:149`, `server.py:1033`) persist it; the join is now
  `position_id = ? OR (position_id IS NULL AND ticket = ?)` so pre-column rows still close, and the
  UPDATE is keyed on the matched row `id` rather than re-matching.
* **Proven pre-fix:** the sync INSERTED a duplicate row instead of closing the original
  (`tests/test_position_id_join.py`, 4 tests).
* Naming trap: the order-sending method is **`send_market_order`**, not `place_market_order` — the
  MASTER_PLAN P2 row and my own notes had it wrong. Corrected in the plan.
* **M1 is now 5 of 6** (C2 deliberately deferred).

### Trap
* When adding a column to an INSERT, count the placeholders — a stray `?` produces
  "23 values for 22 columns" only at runtime, and `log_trade` swallows it into a log line.

## Round 40d — the suite became uncollectable (environmental, pre-existing)

* **P5 escalated, with a measurement.** `jarvis/api/server.py:34` builds `MT5Client(mode="live")`
  in the **class body**, so importing the module initialises MT5. With no terminal running,
  `mt5.initialize()` blocks in a native call **holding the GIL**; `Thread.start()` then can never
  complete, so `import jarvis.api.server` never returns and **pytest cannot even collect** (observed
  13min+ with zero output; `faulthandler` showed the worker at `mt5_client.py:62` and the main
  thread at `threading.Thread.start`). `TimeoutGuard` cannot help — a timeout cannot interrupt a
  thread, and no new thread can be created while the GIL is held. This is why the suite that ran in
  2min at 22:19 hung at 04:33: the MT5 terminal had gone away (no `terminal.exe` running).
* **Verification workaround:** `.scratch/nomt5/MetaTrader5.py` — a stub that answers "no terminal"
  instead of deadlocking. `PYTHONPATH=.scratch/nomt5 pytest tests` then completes
  (**2550 tests, 5 failures**: the 3 weekend-only `test_market_data_independence` ones, plus 2 that
  genuinely need a live terminal — `test_backtest_with_historical_engine` needs real history and
  `test_candle_freshness` asserts a LIVE_MT5 stamp). Neither is a regression.
* Also fixed while doing D2: I had put `CREATE INDEX ... position_id` **before** the `ALTER TABLE`
  migration block, so on an existing DB the index raised, `_init_db` aborted, and the column was
  never added ("Failed to initialize SQLite DB: no such column: position_id"). Indices on new
  columns must come after the migration — the whole block is one try/except.
* Escape hatch that already exists: `JARVIS_BACKTEST_MODE=1` makes `init_connection` skip
  `mt5.initialize()` entirely.
