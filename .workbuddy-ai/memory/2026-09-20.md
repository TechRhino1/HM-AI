### The audit

Four agents ran in parallel with bounded charters (architect / data / AI / Python), each required to
cite `file:line` or a measurement, each told to separate real defects from deliberate design.
Findings IDs: A1–A17, D1–D17, AI1–AI16, P1–P17.

Headline structural problems:
1. **Money path can fail silently and permanently** — P1: `timeout_guard.py:37-47`,
   `future.result(timeout=)` never cancels and `_get_executor` only rebuilds on `_shutdown`, which
   never flips. 16 hung broker calls ⇒ every later call returns its default forever, **including
   the calls that close positions**.
2. **The configured risk limit is not enforced** — `position_sizing.py:86-89` clamps to a hardcoded
   literal `1.50` vs configured `max_risk_per_trade_pct = 0.5`, then multiplies by two more factors
   *outside* the clamp (C1, carried from the trade audit).
3. **>50% of trade history is fabricated** (C2/D1/D2/D5) and still being written today.
4. **The learning loop reads its own output** — `expected_value` is overwritten with realised P&L on
   close (111/111), and `triple_barrier_label`/`mfe`/`mae` are 0 on 35/35 rows (AI2/AI3/AI5).

## Round 40c — D2: trades could never close (M1 complete)

* **D2 — the journal join used the wrong MT5 identifier.** `send_market_order` returned
  `result.order` (the ORDER ticket) and `log_trade` stored it; `sync_mt5_history` closes rows with

  never be matched to its exit deal. Measured on `jarvis_history.db`: **155 rows** with `closed_at`

* Fix: `executed_trades.position_id` added via the existing `ALTER TABLE` map in `_init_db` (no new
  migration machinery needed); `send_market_order` resolves it from the deal

  `log_trade` callers (`execution_engine.py:149`, `server.py:1033`) persist it; the join is now
  `position_id = ? OR (position_id IS NULL AND ticket = ?)` so pre-column rows still close, and the
  UPDATE is keyed on the matched row `id` rather than re-matching.
* **Proven pre-fix:** the sync INSERTED a duplicate row instead of closing the original
  (`tests/test_position_id_join.py`, 4 tests).
* Naming trap: the order-sending method is **`send_market_order`**, not `place_market_order` — the
  MASTER_PLAN P2 row and my own notes had it wrong. Corrected in the plan.

## Round 40d — the suite became uncollectable (environmental, pre-existing)

* **P5 escalated, with a measurement.** `jarvis/api/server.py:34` builds `MT5Client(mode="live")`
  in the **class body**, so importing the module initialises MT5. With no terminal running,
  `mt5.initialize()` blocks in a native call **holding the GIL**; `Thread.start()` then can never
  complete, so `import jarvis.api.server` never returns and **pytest cannot even collect** (observed
  13min+ with zero output; `faulthandler` showed the worker at `mt5_client.py:62` and the main
  thread at `threading.Thread.start`). `TimeoutGuard` cannot help — a timeout cannot interrupt a
  thread, and no new thread can be created while the GIL is held. This is why the suite that ran in
  2min at 22:19 hung at 04:33: the MT5 terminal had gone away (no `terminal.exe` running).
* **Verification workaround:** `.scratch/nomt5/MetaTrader5.py` — a stub that answers "no terminal"
  instead of deadlocking. `PYTHONPATH=.scratch/nomt5 pytest tests` then completes
  (**2550 tests, 5 failures**: the 3 weekend-only `test_market_data_independence` ones, plus 2 that
  genuinely need a live terminal — `test_backtest_with_historical_engine` needs real history and
  `test_candle_freshness` asserts a LIVE_MT5 stamp). Neither is a regression.
* Also fixed while doing D2: I had put `CREATE INDEX ... position_id` **before** the `ALTER TABLE`
  migration block, so on an existing DB the index raised, `_init_db` aborted, and the column was
  never added ("Failed to initialize SQLite DB: no such column: position_id"). Indices on new
  columns must come after the migration — the whole block is one try/except.
* Escape hatch that already exists: `JARVIS_BACKTEST_MODE=1` makes `init_connection` skip
  `mt5.initialize()` entirely.

## Round 40f — M2 begins: D3 schema version stamp

* **All 11 databases reported `user_version = 0`** — no file could declare its own shape, and two
  copies of `jarvis_history.db` (root and `data/`) have already drifted (root has no `closed_at`).
* New `jarvis/data/schema_version.py`: `read_version` / `write_version` / `ensure_version`.
  All five stores now stamp themselves at version 1 — `SQLiteTradeDB` (executed_trades),
  `TradeMemory` (trade_records), `MetadataDB`, `CircuitBreaker`, `DrawdownGuard`.
* **The drift rule is the point:** a file written by NEWER code is *not* stamped down. Stamping it
  down to what this version knows is exactly how columns get silently dropped. It is left alone,
  logged at ERROR, and the caller is told the real number. Version 0 means "predates versioning"
  and is treated as current, since every existing file is 0.

## Round 40g — D3 part 2: the migration runner

## Round 40l — "start HM live and fix all issues": the platform now serves with no broker

**Result: all 12 public endpoints answer HTTP 200 in 0.13-0.22s with no MT5 terminal running.**
Before this round the process either never bound :8501 or bound and never answered a single request.

### Five defects found and fixed (each pinned by a test that fails without the fix)

1. **`server_bind` did a reverse-DNS lookup.** `http.server.HTTPServer.server_bind` sets
   `server_name = socket.getfqdn(host)`. `py-spy` put MainThread in `server_bind -> getfqdn
   (socket.py:811)` with **no listener at all** on :8501 — while the banner had printed and both
   tunnels were up, so it looked identical to the GIL-starvation hang. Fixed with
   `_NoReverseDNSHTTPServer` in `jarvis/api/server.py`; `tests/test_server_bind_no_dns.py` also
   asserts the stock class *does* call `getfqdn`, so the override cannot rot into dead code.
2. **`JarvisOrchestrator` connected to MT5 in its constructor**, so the main thread blocked in
   `MT5Client.__init__ -> init_connection -> TimeoutGuard.run_sync` before `run_web_server` was ever
   reached. Now `auto_init=False`; every operation already goes through `_reconnect_if_needed()`.
3. **`database.sync_mt5_history` called `mt5.initialize()` directly**, bypassing the one gate, from
   `fetch_recent_trades` — i.e. from `/api/history`. Two request threads were parked in it while
   `/api/history`, `/api/telemetry_state`, `/api/market-status` and `/api/radar` timed out and the
   UI pages served in 0.15s. Now it dials `ensure_mt5_terminal()` and returns early without one.
4. **`ensure_mt5_terminal` called `initialize()` with nothing to attach to.** Measured: with no
   terminal, `initialize(timeout=8000)` had **still not returned after 100s** — the `timeout=`
   argument does not bound the launch path, and the call holds the GIL. The gate now asks the OS
   whether a `terminal64.exe`/`terminal.exe` process is running (microseconds, cannot block) and
   refuses when there is nothing to attach to. `JARVIS_MT5_ALLOW_LAUNCH=1` restores the old
   behaviour; stand-ins (no `__file__`) are exempt so a fake never depends on the desktop.
5. **`/api/telemetry_state` paid for a connect on the request thread** — `get_account_snapshot()`
   connects on first use and `init_connection` retries with 1+2+4+8+16s backoff ≈ 31s. A read now
   refreshes only when a connection is already held; connecting is the background synchroniser's job.

New tests: `test_server_bind_no_dns.py` (4), `test_history_read_is_cheap.py` (6, incl. an AST guard
that no direct `mt5.initialize()` reappears in `database.py`), `test_server_answers_without_broker.py`

### Test-hygiene fixes the changes exposed
* `test_candle_freshness` was passing **only because a terminal happened to be running** on this

* Three fakes predated the `timeout=` kwarg (`test_position_id_join`, `test_fill_origin`). A stub

### Environment finding (not a code bug)
**The MT5 terminal is a child of the process that called `initialize()`.** Killing the platform with
`taskkill /T` takes the terminal with it — the terminal logged `14:53:49 System: terminal stopped due
to system shutdown` exactly when the platform was killed. It could not be restarted from here
afterwards: a direct `terminal64.exe` launch exits immediately (bash 127 / `0xC0000135`) leaving no
entry in its own log, and `Start-Process` reports RUNNING at 10s and is gone by the next tool call.
**Only a terminal started outside the sandbox stays up.** So `MT5: RECONNECTING` and
`DATA_FEED: SYNTHETIC` are the honest state, and the platform now says so instead of hanging.

## Round 40m — the user's "terminal64 error", and my own regression

The user reported *"getting terminal64 error and HM start is not working"*. Both halves traced to
this round's gate, and the second half was **mine**.

### What the "terminal64 error" actually is
It is MT5's own message, not a string in this repo (`grep terminal64` finds only `_TERMINAL_NAMES`):

```
[WARNING] [JARVIS_BrokerSymbols] MT5 initialize() failed for market data:
          (-10003, "IPC initialize failed, Pipe server didn't answer in 60 sec")
[ERROR]   [JARVIS_TimeoutGuard]  MT5_Init exceeded 4.00s and could NOT be cancelled;
          guard now has 1 worker(s) stuck.
```

`-10003` = the terminal was launched but never answered its IPC pipe within 60s; `-10004`
(`No IPC connection`) is the follow-up once the pipe is gone. **The terminal's own log
(`%APPDATA%\MetaQuotes\Terminal\D0E8209F77C8CF37AD8BF550E51FF075\logs\`) is the place to look**: it
ran 14:05→14:53 today (`terminal stopped due to system shutdown`, i.e. the `taskkill /T`) and has
**no entry since** — so a failing launch dies before MT5 logs anything at all. Its data dir is
present, writable, and has no lock file, so storage is not the cause.

### The regression I introduced, and the fix
`HM_start.bat` only runs `python HM_start.py live` — it never starts the terminal. Launching
`terminal64.exe` used to be a **side effect of `initialize()`**, so gating the launch out of *every*
path left the platform booting, serving, and reporting SYNTHETIC bars with no way to trade. The
distinction that matters is not "launch vs no launch" but **where**:

* **Boot** (`HM_start.py`, before anything is served) may launch. Blocking 60-100s there costs
  startup time and nothing else.
* **Read/request paths** must not: that is what froze the accept loop.

`ensure_mt5_terminal(mt5_module=None, allow_launch=False)` now carries that flag; `HM_start.py` is
the only caller passing True. `JARVIS_MT5_ALLOW_LAUNCH=1` still forces it process-wide.

### The trap that cost 4 test failures: throttle before the cheap check
The retry throttle (`_INIT_RETRY_SEC = 30`) ran **before** the psutil process check, and
`_LAST_INIT_ATTEMPT` was stamped on the way in. So one "no terminal" answer refused **every** caller
for the next 30s — including a caller holding a perfectly good injected module, which cannot block
and has no reason to be refused. Symptom: 4 failures (3 `test_position_id_join`, 1 `test_fill_origin`)
that each **passed in isolation**, and a *different* failure set on the next run. Fix: only an actual
`initialize()` attempt spends the window; the cheap refusal returns before stamping it. Two tests pin
it (`test_a_cheap_refusal_does_not_open_a_retry_window`,
`test_a_stand_in_caller_survives_an_earlier_refusal`), both mutation-proved red by restoring the old
order.

### Also de-duplicated
The DataFeed fallback warning fired per call per 8s cache expiry: **~3,300 lines in 17 minutes**. Now
one per `(symbol, timeframe)`, with the set cleared on recovery so a *later* outage still warns
(3 tests). Measured after the fix: 30 lines, 30 distinct; `MT5 not available` 701 → 1; ERROR 701 → 0.

### Where the suite stands
2640 cases, **6 failures**: 3 weekend-only `test_market_data_independence` rows, plus 3 that are
**cross-file state leaks, not caused by this round** — `test_multi_style_radar` and
`test_opportunity_arbiter` each want 6 opportunities and get 0, and
`test_regression_fixes::test_d1_online_ml_and_trade_memory_learning_loop` gets None. All 3 pass
alone and in their own file, and the failure set is **identical with the platform running and
stopped**, so the live server is *not* the cause. Prime suspects: `data/jarvis_bandit_state.json`
(9 regimes of learned priors, shared with the running platform) and `jarvis_circuit_state_paper.db`.
The conftest already has this exact pattern for the drawdown guard and the trade journal, so the
likely fix is an autouse fixture redirecting the bandit/circuit state too.

## Round 40n — suite is green: 2646 passed, 0 failed

**The bandit-state guess above was wrong.** The cause was a latched flag.

### `terminal_ready()` was answering the wrong question
`terminal_ready()` latches True on the first successful attach and never re-checks (documented and
tested — correct for its own job). But **all three of its consumers were asking "is the broker link
up RIGHT NOW"**, and a latched yes is the wrong answer the moment the terminal dies.

Silent and total: the latch stays True, so every frame that falls back to synthetic bars is read as
proof that the broker does not offer that symbol, `run_cycle_for_symbol` refuses to decide for every
symbol, the radar empties, and nothing is ever traded — while the only log line blames the *symbol*
(`this broker does not appear to offer XAUUSD`), which is the opposite of the truth. An operator who
restarts the terminal mid-session hits exactly this.

Reproduced deliberately with a throwaway pytest plugin that sets `_TERMINAL_READY = True`:
`test_multi_style_radar` goes 6 → 0 (`0 != 6`) with that exact warning, and passes in isolation. New
`terminal_live()` = `terminal_ready()` **and** the process is still running, used at all three sites
(the synthetic-frame gate, the MT5 health report — a latch kept claiming `CONNECTED` for a link that
was gone — and the auto-selection skip in `server.py`). Measured cost: **1.96 ms per call**, so
~118 ms per 60-call cycle against a 3–15 s cycle. `terminal_ready()` is untouched.

### The last 3 failures were a wall-clock dependency
The cold-history warm-up only runs on a **STALE** verdict, and `classify_bar_freshness` answers
`MARKET_CLOSED` inside the weekly close — so a ~20h-old bar is STALE Mon-Fri and MARKET_CLOSED at
weekends. Those 3 tests failed every Saturday/Sunday and passed on a weekday with no code change.
**Proved by extraction, not argument**: `git show HEAD:tests/… > .scratch/orig/…` and ran the pre-fix
file with `_is_weekend_gap` forced True — the same 3 assertions fail. A `weekday_market` fixture pins
the calendar; the weekend rule keeps its own test in `test_candle_freshness`.

### Two measurement lessons worth keeping
* **The harness truncates pytest's stdout tail**, so `-rf` never prints the failure list — the summary
  was replaced by a `[safe-delete]` note about pytest's temp dir. `--junit-xml=` writes to a file and
  survives; parse that instead.
* **A guess about the cause is not a cause.** "The bandit state is shared with the platform" was
  plausible, matched the symptoms, and was **wrong**. The cheap test that killed it: run the suite
  with the platform stopped and compare the failure set — byte-identical, so the platform was not
  involved. The other cheap test that found the real cause: force the suspected flag and watch the
  test go red.



## Round 40o — C2 closed: no entry price without an observed price

M1 is now **6 of 6**. The deferral note said the fabricated rows come from the *decision engine's*
price, not the provider's fallback, and that the chain needed its own investigation. It did, and the
provider was never involved.

### The mechanism
`market_context.build_context` (`:78-80`) sets `current_price = bid = 0.0` and
`ask = spread × pip_size` when the primary frame is **empty** (feed down, cold symbol). Every entry
price is minted from `context.ask` (BUY, `dynamic_levels:131`) or `context.bid` (SELL, `:269`), so an
unobserved market became a real-looking order.

**Measured, end to end, before the fix** — `.scratch/repro_c2_zero_entry.py`:

| symbol | entry | stop | guard | sized lots | exposure for a 50 USD risk budget |
|---|---|---|---|---|---|
| BTCUSD | 0.02 | **-0.04** | **passed** | **100.00** | **6,500,004 USD** |
| EURUSD | 0.0002 | -0.0004 | passed | 0.83 | 90,088 USD |
| XAUUSD | 0.2 | -0.4 | passed | 0.77 | 184,831 USD |

BTCUSD hit the sizer's own 100-lot ceiling, i.e. the ceiling — not the geometry check — is what
limited it. `risk_engine:213` computes `risk_dist = abs(entry - stop)` and all 15 adaptive gates pass
on zeros (gate 15's `price_diff < risk_dist * 0.15` is `0 < 0` = False).

### Why the guard missed it
`trade_guard` had a finiteness loop and inverted-geometry checks. **`_is_finite(0.0)` is True**, and
with the entry at ~0 the comparisons (`stop_loss >= entry_price` for BUY) are all **False** — so a
*negative* stop loss passed. A zero entry is not an edge case here; it is what an empty frame is.

### The fix — one predicate, three layers, plus the provider
* `schemas.is_observed_price(value)` — finite **and strictly positive**. One definition, so the gate
  and the producers cannot drift apart.
* `dynamic_levels.calculate_levels` — refuses to **mint**: returns a HOLD-shaped result with the same
  key set the callers index, plus `data_unavailable: True`. (Returning `None` would need every caller
  to guard; the dict shape is what both callers already read.)
* `decision_engine._compute_bias_and_levels` — refuses to emit a **direction**. `decision_action`
  becomes EXECUTE on `gate_passed and bias in (BUY, SELL)`, so a BUY/SELL beside a zero entry would
  have been marked executable. Returns `("HOLD", 0.0, …, None, 0.0)` — same 8-tuple arity.
* `trade_guard.validate_pre_execution` — refuses to **authorize**: the finiteness loop now also
  requires a positive price, catching any other `DecisionObject` producer.
* `tradingview_provider.fetch_candles` — returns `None` when the anchor quote is a fallback. The series
  is anchored to it bar by bar (including the "genuine live OHLCV" last bar), and
  `fetch_real_candles` logs whatever comes back as "Live TradingView candles". Refusing lets the tier
  hierarchy reach Tier 4, which labels itself. Also tightened `price <= 0.0` → `is_observed_price`,
  which now catches NaN.

Warnings are de-duplicated per symbol with re-arm on recovery — this runs per symbol per radar cycle,
the same flood shape as the data feed (3,300 lines in 17 minutes).
