# 2026-09-17

## Session 19 — "use mt5 real data": the platform was reading synthetic bars

User answered the P0-1 gate question with **"use mt5 real data"** and the backlog question with
**"all, one by one"**. This session took the first item: make the platform actually read the live
terminal.

### The misdiagnosis I nearly shipped

`/api/telemetry_state` reported `services.MT5 = DISCONNECTED` and the dashboard said **"broker
offline"**. MT5 was in fact connected (package 5.0.6180, terminal build 6182, account 101059540,
equity 728.36). I started reading the data path looking for a product defect.

The process was started with
`start_server(host='127.0.0.1', port=8501, mt5_client=None, orchestrator=None)` — **my own
CSS-verification harness**, which has no broker client at all, so `DISCONNECTED` was *correct*. Found
it by reading the running pid's cmdline (`psutil.Process(7728).cmdline()`), not by reading code.
**Check how the process was started before diagnosing the data path.**

### The three real defects (commit `9c99483`)

1. **Execution mode gated market data.** `MT5Client.init_connection()` early-returns for
   `paper`/`backtest`/`offline`, and *nothing else* called `mt5.initialize()`. So in the process where
   the feed runs the terminal was never initialized → `resolve_broker_symbol()` failed every probe →
   the canonical `XAUUSD` (not the broker's `GOLD.i#`) reached `copy_rates_from_pos` → 0 rows →
   **every frame `SYNTHETIC_FALLBACK`**. Confirmed by logging the orchestrator's own data path:
   `MT5 returned 0 rates for XAUUSD (D1/H4/H1/M15). Falling back to synthetic rates.` and
   `mt5.terminal_info(): False`, while a bare `mt5.initialize()` in a fresh process made
   `resolve_broker_symbol('XAUUSD')` return `GOLD.i#` and a fetch return 5 rows in 0.00s.
   Fix: `broker_symbols.ensure_mt5_terminal()` (cached, retried at most every 30s), called by
   `data_feed._fetch`. **Measured: paper mode went from 0/20 live frames to 20/20.**
2. **A failed probe was cached forever.** `_FAILED[sym] = True` is indistinguishable from "the broker
   has no such symbol", so one call before the terminal was ready pinned every symbol to `None` for
   the process lifetime. No longer cached when the terminal is down.
3. **The health flags were inferred, not measured.** `DATA_FEED` was keyed off the *execution*
   account login, so paper mode said `OFFLINE` forever while real bars streamed — and `dashboard.js`
   read `broker online/offline` off the same flag. Now `DataFeedEngine.data_health()` measures it
   (`STREAMING|STALE|CLOSED|SYNTHETIC|OFFLINE`) and the chip keys off real bars being present.

### Three more found while verifying

* **Fabricated bars were being traded on.** `WTI` is in `Orchestrator.symbols` and absent at XM, so
  the feed synthesised a WTI series and the platform analysed it as real. A live session now refuses
  a `SYNTHETIC_FALLBACK` frame — **scoped to `terminal_ready()`**, so it fires only when we *have* a
  working broker link that still answered nothing. With the terminal down the synthetic frame is kept
  for the UI and execution is already blocked (`get_account_snapshot()` → `login 0`).
  This is the case the 2026-09-16 note deliberately left ungated; the scope guard is what makes it
  safe to gate now.
* **Cold history reads as a stalled feed.** MT5 pulls history on demand, **asynchronously**. Measured
  on 6 untouched symbols: **5 read ~19.6h stale, unchanged across 7 back-to-back calls (30-47ms)**,
  then `FRESH` a few hundred ms later. So the freshness gate would refuse a good symbol on the first
  cycle after every restart — intermittently, and only right after a restart. Bounded warm-up added
  (1.2s budget, 0.3s poll, paid once per symbol).
* **`COPPER` resolved to an EQUITY.** The fuzzy scan was `if sym in n.upper()`, so `COPPER` matched
  `SouthernCopper` (Southern Copper Corp) and was returned as the copper commodity — stamped
  `LIVE_MT5` and certified `FRESH`, so nothing downstream could tell. Now prefix-only + logged at
  WARNING.

Also: the 0-rates and refusal warnings repeated on every scan (**21+ lines/cycle** for one
unavailable symbol across 3 styles); both are now once-per-key, as `_stale_warned` already was.
