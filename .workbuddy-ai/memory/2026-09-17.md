### The misdiagnosis I nearly shipped

### The three real defects (commit `9c99483`)

1. **Execution mode gated market data.** `MT5Client.init_connection()` early-returns for
   `paper`/`backtest`/`offline`, and *nothing else* called `mt5.initialize()`. So in the process where
   the feed runs the terminal was never initialized → `resolve_broker_symbol()` failed every probe →
   the canonical `XAUUSD` (not the broker's `GOLD.i#`) reached `copy_rates_from_pos` → 0 rows →
   **every frame `SYNTHETIC_FALLBACK`**. Confirmed by logging the orchestrator's own data path:
   `MT5 returned 0 rates for XAUUSD (D1/H4/H1/M15). Falling back to synthetic rates.` and
   `mt5.terminal_info(): False`, while a bare `mt5.initialize()` in a fresh process made
   `resolve_broker_symbol('XAUUSD')` return `GOLD.i#` and a fetch return 5 rows in 0.00s.
   Fix: `broker_symbols.ensure_mt5_terminal()` (cached, retried at most every 30s), called by
   `data_feed._fetch`. **Measured: paper mode went from 0/20 live frames to 20/20.**
2. **A failed probe was cached forever.** `_FAILED[sym] = True` is indistinguishable from "the broker
   has no such symbol", so one call before the terminal was ready pinned every symbol to `None` for
   the process lifetime. No longer cached when the terminal is down.
3. **The health flags were inferred, not measured.** `DATA_FEED` was keyed off the *execution*
   account login, so paper mode said `OFFLINE` forever while real bars streamed — and `dashboard.js`
   read `broker online/offline` off the same flag. Now `DataFeedEngine.data_health()` measures it
   (`STREAMING|STALE|CLOSED|SYNTHETIC|OFFLINE`) and the chip keys off real bars being present.

## Session 20 — P0-1: measuring the gate on real MT5 data

User answered the P0-1 gate question with **"use mt5 real data"** and the backlog question with
**"all, one by one"**.

### Data basis verified first

All 20 `data/market/real/<SYM>/<SYM>_H1_365d.parquet` manifests: `provenance: MT5_TERMINAL_REAL`,
`synthetic: false`, `full_window: true`, `quality.ok: true`, **0 issues**, 5,723–8,760 rows. So the
measurement basis is genuinely real terminal data, not the stored-synthetic path.

### Two new tools

* **`tools/p0_1_gate_measurement.py`** — replaces the arbitrary `PF >= 1.3` bar with the question
  that actually decides the gate: *is mean R per trade distinguishable from zero after costs?*
  Three traps handled: (1) trades within a symbol are **not independent**, so the aggregate treats
  each **symbol as a cluster** (n=20) rather than pooling ~95k trades; (2) 20 symbols is 20
  hypotheses, so the bar for a "best symbol" is the **distribution of max|t|** across 20 null draws,
  not 1.96; (3) a symbol can look good from after-the-fact selection. Includes a self-contained
  Student-t p-value (verified against 8 known values) and seeded bootstraps.
* **`tools/p0_1_direction_audit.py`** — separates **direction skill from beta**: same entries, same
  risk distance, same target multiple, LONG only. If the gate's mean R is no better than always-long,
  the P&L came from the instrument's drift.

### The decisive finding: the winners are beta

At 365d, the three symbols that cleared the multiple-testing bar were **all beaten by simply being
long**: XAUUSD gate +0.0889R vs always-long +0.1128R; XAGUSD +0.0402 vs +0.0744; WTI +0.0229 vs
+0.0871. So the "POSSIBLE SIGNAL" verdict from stage 1 is an artefact of gold/silver/oil trending.

Stability check killed the rest: every "direction adds value" verdict **flips with the window**
(XAUUSD 183d adds value → 365d beta; ETHUSD 183d loses → 365d adds value; BTCUSD, NAS100, USDCAD all
flip). Only "gate loses" is stable. The one symbol profitable *and* beating always-long at both
windows is GER40, at +0.044R/+0.017R — too small and too inconsistent to act on.

Aggregate: cluster-robust **t = −1.78, p = 0.091, 95% CI [−0.0555, +0.0008] contains 0**, point
estimate **negative**. Of the 13 symbols whose CI excludes zero, **10 are significantly LOSING** and
only 3 winning. Note the pooled per-trade t = −6.27 is *inflated* and would have been the wrong
number to quote.

### But the measurement was contaminated — found mid-flight

`signal_scan.py` added the spread **for BUY only**:

```python
entry_price = float(nxt["open"])
if bias == "BUY":
    entry_price += spread_pips * spec.pip_size      # SELL: nothing
```

`trade_simulator` mentions spread only in its docstring (no exit-side spread term), so **every SELL
candidate in every cached table entered at the mid and carried no spread at all**. Verified on the
stored tables: `(fill − next_open)/pip` ÷ row spread = **+1.000 BUY, 0.000 SELL** on every symbol
checked. `engine.py` already had the correct form *with the comment explaining it* — the scanner was
missed. Classic "two entry points, one fixed".

It also explains something that looked like a finding: SELL mean R exceeded BUY mean R on 13/20
symbols, which is exactly what a free short leg produces.

**Fix (`fdf8e58`)**: `entry_fill()` in the new `jarvis/backtesting/fills.py` is the single
implementation; `engine.py` and `signal_scan.py` both call it. `tests/test_entry_fill_convention.py`
(11 tests) includes `test_no_module_reimplements_the_fill`, which greps the tree for the arithmetic
outside `fills.py`. Five tests fail on the pre-fix code, all SELL-side. pytest **841 passed** (+11).

**Blast radius: EVERY cached candidate table is affected** — `H1_365d`, `H1_183d`, `H1` 95d
(`candidates.parquet`, the calibration input), and `M15_183d` + `M5_183d` (which feed
`fit_score_calibration`, regime optimisation, and are P1-3's target). So the fitted calibration and
all SCALP/DAY_TRADING numbers are contaminated too, not just P0-1's.

### Trap worth remembering

The re-scan writes **one file per symbol as it finishes**, so a partially-complete re-scan silently
produces a **mixed** dataset — and a measurement run against it looks plausible and moves only
slightly, which is exactly how you talk yourself into believing a null result. I compared mtimes with
`--time-style=+%H:%M:%S`, which **drops the date**, and read 15 stale files as fresh. Always print the
full date, and check `ls -l` counts before measuring on a regenerated cache.

## Session 21 — P0-3 stage A: the stop's noise band, measured

P0-1 is blocked behind the re-scan, so I started **P0-3** (derive stop/target/time-stop from
volatility instead of constants). Wrote `tools/p0_3_exit_geometry_measurement.py` with four
independently runnable parts. **Part A needs no candidate data** — pure OHLC — so it ran against the
live cache while the re-scan was still going.

**Measured, `noise = |close−open| / ATR` (causal ATR: bar *i* uses ATR as of *i−1*), 20 symbols:**
the ratio is **symbol-invariant and timeframe-invariant**. Body median 0.322–0.373 across FX, JPY
crosses, gold, silver, oil, three indices and three cryptos — a ±0.025 spread over four asset
classes. Adverse q90: **1.431 (H1) / 1.428 (M15) / 1.406 (M5)**.

**The decisive table — false-stop rate = P(bar's own adverse range > k×ATR):**

| k | H1 | M15 | M5 |
|---|---|---|---|
| 0.85 | 16.9% | 16.9% | 17.2% |
| 1.00 | 12.2% | 12.1% | 12.2% |
| 1.11 | 10.0% | 10.0% | 10.0% |
| 1.25 | 7.3% | 7.1% | 7.0% |

So **one universal `k ≈ 1.11` buys a 10% mechanical false-stop rate on every timeframe and every
symbol.** The style caps below it are the defect:

* **SCALP `min(0.65×ATR, …)` → 28.3%** — the only materially broken one. `dynamic_levels.py:174,303`.
* DAY_TRADING index `min(0.90×ATR, …)` → 15.3%; forex `1.05` → 11.1%; other `1.30` → 6.6%.
* SWING structural fallback `0.85–1.00×ATR + 0.35 buffer` = 1.20–1.35 → **8.3% / 6.1%** — fine.

**The spec's "scale by ATR percentile" clause is measurable but negligible.** corr(rolling k, ATR
percentile) is positive in **20/20** symbols (median +0.234, so the effect is real, not noise) but the
magnitude is +5.2%: rolling q90 k goes 1.033 → 1.087 from the bottom ATR quintile to the top. That
moves the false-stop rate ~1pp. Adding a scaling term would be complexity for nothing. **Do not
implement it** — report why.

**Self-correction worth keeping:** my first measure took `max(up, down)` — the worst case for *any*
stop. But a BUY stop sits below and a SELL above, so for a balanced book the honest figure is the
*mean* of the two one-sided rates. That inflated SCALP from **28.3% → 53.7%**, a 1.9× overstatement.
Both are now reported; only the directional one is quoted. An overstated defect number is as damaging
as an understated one.

**Next for P0-3:** parts B (tp_r sweep vs vol bucket), C (max_bars edge decay), D (cost gate) all need
the clean cache — the SELL-spread fix moved `fill`, and `risk_dist = |entry_fill − sl|`, so `risk_dist`
moved too. Do not run them on the mixed cache. Then the *acceptance test* for changing the SCALP cap
is whether the measured payoff actually improves with a wider stop — not the false-stop rate alone.

### Bias found and fixed in my own control (worth remembering)

`forced_long_benchmark` entered the control long at the candidate's stored `fill`. For a BUY row
that is the ask (correct), but **for a SELL row `fill` is the bid** — so always-long was getting a
free half-spread, biasing the comparison *against* the gate. Conservative, but still wrong, and on a
2.3-pip FX spread it is worth ~0.05R/trade — the same order as the effects being measured.

Fixed to `fill + 2 × spread` for SELL rows. Validation: NZDUSD moved **+0.0988R (365d)** and
**+0.1129R (183d)**, against an expected half-spread of ~0.09R for a ~0.19R FX round turn. The
correction moved the *verdict*: survivors went from 1/20 (GER40 only) to 3/20, and flips from 7 to 8.
**A biased control can hide a real effect as easily as invent it** — fix it, don't footnote it.

## Session 23 — P2-1 built, and a real broker-offset defect found via 4 red tests

### P2-1: what already existed, and what did not

`PurgedKFold` (embargo) already exists in `jarvis/learning/walk_forward.py`, and
`jarvis/learning/sample_weights.py` claimed to implement López de Prado's sample-uniqueness
weighting. **The Deflated Sharpe Ratio was genuinely missing.** But the existing uniqueness code had
two defects that made it unusable, both now fixed:

1. **Wrong quantity.** It returned `1 / (concurrency at the label's start)`, never looking past the
   first bar of the span. A 1-bar label and a 10-bar label sharing a start must score 0.50 and 0.95 —
   the long label is alone for nine of its ten bars. The old code returned **0.5 for both**.
2. **O(n²) with a Python double loop.** 4,000 labels took 3.5s, so the audit's 94,937 trades would
   have taken **~33 minutes**. It was never run at scale, which is why defect 1 survived.

Now vectorised — difference array for concurrency, prefix sum for the span means, O(n + T). 20,000
labels take **0.010s**. `entry_edge_diagnostic._uniqueness_weighted` gets the fix for free.

Also dropped `|pnl|` rescaling from the default path: that is return-magnitude weighting, not
uniqueness weighting, and folding it in biased expectancy upward by over-weighting big winners. Still
available as `magnitude_weighting=True`.

New `jarvis/learning/deflated_sharpe.py` (PSR, DSR, expected-max Sharpe, min track-record length,
`effective_trials`). 33 new tests in `tests/test_sample_uniqueness.py` + `tests/test_deflated_sharpe.py`.
**Six of my first-draft test expectations were wrong and the implementation was right in all six** —
they forced me to derive the closed forms properly. The best of them: I asserted the PSR reduces to a
bare z-test for normal returns, but the denominator is `sqrt(1 + SR²/2)` (Lo 2002), not 1. Had I
"fixed" the code to match my wrong test, the DSR would have been silently wrong.

### A real defect, found because 4 tests went red

`pytest` went from 841 → **874 passed, 0 failed**. But first, 4 tests failed, and chasing them found
a genuine bug rather than a test artefact.

**`broker_utc_offset` returned 0 for every caller**, for two independent reasons:

1. It called `symbol_info_tick` **without initialising the terminal in this process**. The execution
   client only initialises for modes that place orders, so any read-only process got `None` for every
   symbol — the same class of defect as the market-data path.
2. It was handed **canonical** symbols. MT5 knows gold as `GOLD.i#`; `symbol_info_tick("XAUUSD")` is
   `None`. (The data path passes the broker symbol, but `broker_utc_offset` is called from elsewhere
   with canonical names.)
3. And a third, found while fixing: the real caller passes **one** symbol, and a single slow symbol
   breaks the derivation. Gold's tick ran ~17 min behind EURUSD's, landing 799s from the nearest
   30-minute boundary against a 300s tolerance → rejected as stale. The offset is a property of the
   **server**, so any fresh tick answers the same question; it now retries across liquid majors.

After the fix, from a cold process: `XAUUSD → 10800`, `NAS100 → 10800`, `EURUSD → 10800`, `WTI → 10800`
(WTI has no broker symbol at all). Before: all `0`.

**Why this mattered more than the holding-duration bug it was written for:** `classify_bar_freshness`
computes `age = (now + offset) − bar_epoch`, and bars are stamped on the broker clock. With
`offset = 0`, `age` came out **negative** — the bars looked like they were in the future — which the
classifier maps to `UNKNOWN`. And **`first_stale_frame` only blocks on `STALE`, never `UNKNOWN`**, by
design, so synthetic frames can still be reasoned on. Net effect: a zero offset **silently disabled
the stale-feed gate**. The four tests were passing *because of the bug*; fixing the offset made the
ages truthful and gold's genuinely-stale M5/M15 frames were then correctly refused.

**The trap:** two independent safety mechanisms shared a single failure mode. A check that fails
*open* is worse than no check, because it reports success. `offset=0 → age<0 → UNKNOWN → gate
tolerates` is exactly that shape, and it hid a stale feed for as long as it existed.

The 4 tests were then fixed properly — they mock the decision/execution engines and assert radar and
learning plumbing, but still fetched live bars first, so their outcome depended on the wall clock and
the broker connection. Each now neutralises **only** `first_stale_frame`, with a comment saying why.

## Visual pass — three defects no assertion had caught

Reading the four screenshots (`.scratch/shots/six-*.png`) instead of trusting the green suites found

the pending row correctly appearing at 44px for `BUY_LIMIT`.

**3. The history filter toolbar was clipped to 38px of its 116px** — the filters the user explicitly
asked to have restored were rendering as an unlabelled sliver of a scrollbar. Cause: the history
panel stacks two `.tt-panel__body` children and both are `flex: 1 1 auto; min-height: 0`, so the
table won the space and squashed the toolbar. Fixed with
`.tt-slot--hist > .tt-panel__body:not(.tt-panel__body--flush) { flex: 0 0 auto; }`.

**The suite said "no silently clipped content" the whole time.** That check was horizontal-only
(`scrollWidth > clientWidth`) and accepted only `overflowX: hidden|clip`, so an `overflow: auto` box
squashed vertically was structurally invisible to it. Extended to the vertical axis, with the rule
gated on *controls*: flag a box that cannot show one whole control it contains. The first attempt
(first-child height) fired on seven legitimate scroll lists — `#selection-body` at 35px over 442px
of rows — so it was narrowed until it fired on exactly the toolbar. Negative-tested by reverting the
CSS: suite goes red on exactly 3 checks (analytics at the 3 viewports), 0 false positives, then green
again with the fix. A guard that has never seen its bug pins nothing.

**4. The ticket panel is over-subscribed — also mine, from item 4.** The context strip I added inside

~834px panel. Flex cut the **form** to 252px — halving the BUY/SELL row (18px of 44 visible) and
