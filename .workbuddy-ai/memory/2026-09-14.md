## 1. The deletion recurred — second occurrence, same signature

**Symptom.** Immediately after `git rm -q jarvis/ui/templates/app.html jarvis/ui/static/css/app_shell.css
jarvis/ui/static/js/app_shell.js`, `git status` again showed the whole `jarvis/` package as deleted:
144 unstaged ` D` entries plus the three intended staged `D ` entries. Confirmed on disk twice
independently — `ls jarvis/` → *No such file or directory*, and Python `os.path.isdir("jarvis")` →
`False`. Repo-root mtime **03:50:52**, matching the moment of the `git rm`.

This is the **second** occurrence. Incident 1 was ~03:28 the same night (D: Recycle Bin mtime).
Both followed heavy file-write activity around git operations. Two data points, same shape.

**Recovery — this time better.** The deletions were *unstaged*, so the index still held every blob.
Rather than the `git checkout HEAD -- jarvis/` used last time (which would also have resurrected the
three files I had deliberately `git rm`-ed), I used:

```
git checkout -- jarvis/          # restore working tree FROM THE INDEX
```

Because the index had the three dead files removed and everything else present, this restored the
144 lost files *and* left the three intentional deletions staged. One command, both goals, no
rework. `git status` afterwards showed exactly the three staged deletions and nothing else.

**New forensics this round (all negative).**

| Checked | Result |
|---|---|
| `git config --list --show-origin` for `hooksPath`, `fsmonitor`, aliases | none |
| `.git/hooks/` non-`.sample` entries | none |
| `.git/info/exclude` | empty |
| `.gitattributes` | absent |
| `git fsck` | no errors (only dangling trees/blobs from the `git rm` and amends — normal) |
| WorkBuddy automations (`automation_update list`) | **zero** |
| Free disk space on `D:` | 218 GB free — not a space-driven cleanup |
| Process enumeration (`tasklist`, PowerShell `Get-Process`) | **blocked by the sandbox** |

`tasklist` returns nothing and the PowerShell tool returns no output at all in this environment, so
process-level forensics are unavailable. The PowerShell tool appears non-functional here; use Bash
for everything.

**Cause: still undetermined.** Ruled out: git hooks, fsmonitor, automations, disk pressure, a
destructive script in the repo. Remaining hypotheses unchanged — AV/EDR quarantine, a cloud-sync
client, or an external process reacting to filesystem write events. The tight correlation with git
operations is the strongest clue but is not proof.

**Mitigation applied.** Created a full history bundle at `.git/backup/repo-<timestamp>.bundle`
(1.8 MB, verified with `git bundle verify`). `.git/` demonstrably survives these incidents — it is
the index that made recovery possible both times — so the bundle is stored *inside* it. Note the
sandbox **refuses writes outside the project directory** (`git bundle create /d/HM_AI/...` failed
with *No such file or directory*), so an out-of-repo backup is not possible from here.

**Lesson, reinforced.** Commit every new file the moment it is written. Both incidents cost
rework only for *untracked* files. The three console assets and both test files were each committed
within minutes of being written this session, so the recurrence cost nothing.

## 3. Verified facts worth keeping

* **Measured mode reliability weights** (from the real 6-month report, exposed by
  `/api/intelligence/reliability`): SWING **0.346**, DAY_TRADING **0.1064**, SCALP **0.1287**. All
  three are below the neutral 0.5, which is correct — all three modes lost money over the window.
* **Backtest job status vocabulary is `QUEUED | RUNNING | DONE | FAILED | CANCELLED`.** `DONE`, not
  `COMPLETED`. `POST /api/backtest/run` returns **202 Accepted** with `job_id`, not 200.
* **Local requests are treated as an admin.** `JarvisRequestHandler._get_auth_user()` returns an
  admin identity when `_is_local_request()` is true, so a localhost curl needs no token. `/api/intelligence/*`
  and `/api/backtest/*` are deliberately *not* in `public_get_endpoints` — the console shell loads
  before auth, the trading-intent surface does not.
* **Auto-selection fails safe.** With no orchestrator attached it returns **503** with
  `status: UNAVAILABLE` and a reason, not an empty 200. With an engine attached, EURUSD/SWING
  produced a real decision.
* **`/api/action/auto-select` is hard-wired to a dry run.** Sending `dry_run=False` still returns
  `dry_run: true` and sets `requested_dry_run_ignored: true`. Verified live.
* **`normalise_style` maps any unrecognised style name to `SWING`** rather than rejecting it. A typo
  in a style name therefore produces a swing scan, not an error. Both the optimiser and the
  aggregator inherit this; callers taking style names from a user must validate upstream.
* **`console.js` is an IIFE and exports no global.** No `window.HM_CONSOLE`. `console.js` and
  `console.css` are pure additions on top of the `hm_ui.css` token set; they define no new tokens.
* **`/` and `/console` serve `console.html`; `/classic` and `/classic.html` serve `index.html`.**
  The legacy terminal is the rollback path, and `verify_console_live.py` asserts it still loads.
