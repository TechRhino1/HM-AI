### The credential finding (corrects the previous session's conclusion)

The prior session recorded this as blocked: *"Git Credential Manager no longer holds a cached
GitHub credential and re-auth needs an interactive prompt"*, and escalated to the user to run
`git push` interactively.

That diagnosis was **half right and the conclusion was wrong**. Re-probed this session:

| Probe | Result |
|---|---|
| `git config --get-all credential.helper` | `helper-selector` + the portable `git-credential-manager.exe` |
| `git credential fill` (host=github.com) | **empty output** — no *cached* credential |
| `GH_TOKEN` / `GITHUB_TOKEN` / `GIT_ASKPASS` in env | none set |
| `gh` CLI | not installed |
| `~/.git-credentials` | absent |

So there genuinely is no *stored* credential — the probe was correct. But the very next
`git push` **succeeded anyway**: GCM obtained a credential on its own without any interactive
prompt surfacing in the captured output.

**Lesson: an empty `git credential fill` proves only that no credential is CACHED. It does NOT
prove GCM cannot obtain one.** Always attempt a bounded push before escalating to the user.
Don't re-derive "the user must re-authenticate" from the probe alone.

### Verification technique worth keeping

A pipe **masks the exit code**, which is exactly how a hung push gets misread as success:

```bash
timeout 30 git push origin main | head      # rc=0 ALWAYS -- wrong
timeout 30 git push origin main > f 2>&1; rc=$?; cat f   # correct
# 0 = pushed, 124 = hung awaiting interactive auth
```

Then confirm against the **remote**, not the local ref cache:
`git ls-remote origin refs/heads/main` returned `b8e489b6d9292ec1ef4514b7883016487f887564`,
identical to local `HEAD`. Working tree clean, `git status -sb` shows `## main` with no
ahead/behind.

Also: `git log origin/main..HEAD` fails with *"ambiguous argument"* when the local `origin/main`
ref does not exist yet (this clone had no such ref). Use `git fetch origin` first, or just
`git ls-remote`.
