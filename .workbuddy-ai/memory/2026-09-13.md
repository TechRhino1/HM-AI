### The credential finding (corrects the previous session's conclusion)

The prior session recorded this as blocked: *"Git Credential Manager no longer holds a cached
GitHub credential and re-auth needs an interactive prompt"*, and escalated to the user to run
`git push` interactively.

That diagnosis was **half right and the conclusion was wrong**. Re-probed this session:

| Probe | Result |
|---|---|
| `git config --get-all credential.helper` | `helper-selector` + the portable `git-credential-manager.exe` |
| `git credential fill` (host=github.com) | **empty output** — no *cached* credential |
| `GH_TOKEN` / `GITHUB_TOKEN` / `GIT_ASKPASS` in env | none set |
| `gh` CLI | not installed |
| `~/.git-credentials` | absent |

So there genuinely is no *stored* credential — the probe was correct. But the very next
`git push` **succeeded anyway**: GCM obtained a credential on its own without any interactive
prompt surfacing in the captured output.

**Lesson: an empty `git credential fill` proves only that no credential is CACHED. It does NOT
prove GCM cannot obtain one.** Always attempt a bounded push before escalating to the user.
Don't re-derive "the user must re-authenticate" from the probe alone.

### Verification technique worth keeping

A pipe **masks the exit code**, which is exactly how a hung push gets misread as success:

```bash
timeout 30 git push origin main | head      # rc=0 ALWAYS -- wrong
timeout 30 git push origin main > f 2>&1; rc=$?; cat f   # correct
# 0 = pushed, 124 = hung awaiting interactive auth
```

Then confirm against the **remote**, not the local ref cache:
`git ls-remote origin refs/heads/main` returned `b8e489b6d9292ec1ef4514b7883016487f887564`,
identical to local `HEAD`. Working tree clean, `git status -sb` shows `## main` with no
ahead/behind.

Also: `git log origin/main..HEAD` fails with *"ambiguous argument"* when the local `origin/main`
ref does not exist yet (this clone had no such ref). Use `git fetch origin` first, or just
`git ls-remote`.

## Six-month multi-mode backtest on real MT5 data (in progress)

User asked for: a 6-month backtest on real MT5 data across all symbols, validated separately in
scalp / day-trading / swing modes, plus verification that the arbiter picks the highest-priority
trades in every mode and every regime.

### Structural findings that shaped the work

1. **The three modes differ ONLY by timeframe.** `SWING`/`DAY_TRADING`/`SCALP` map to
   `{D1,H4,H1,H4,M15}` / `{H4,H1,M15,H1,M5}` / `{H1,M15,M5,M5,M1}`. Nothing else distinguishes
   them. That map was inlined inside `fetch_multi_timeframe`, so the live path and any backtest
   could drift. Extracted to `jarvis/market/data_feed.STYLE_TIMEFRAMES` (+ `normalise_style`,
   `style_timeframes`, `style_timeframe_set`) as the single source of truth.
2. **`BacktestEngine` was style-agnostic.** It hardcoded MTF context as `primary + resample(H4) +
   resample(D1)` and never passed `trade_style` to `build_context` / `decision_engine.evaluate`.
   So the modes were *not* representable in a backtest. Added `trade_style` + `mtf_source` params
   plus `_prepare_mtf` / `_slice_mtf`. Legacy path (no `trade_style`) is byte-for-byte unchanged.
3. **The arbiter is never called by the engine** — only by
   `orchestrator._orchestration_loop_single_pass`, which sweeps 20 symbols x 3 styles and keeps
   one winner. Therefore prioritization *cannot* be validated through a backtest; it needs
   counterfactual per-candidate outcomes. That is what `tools/verify_prioritization.py` does.
4. **M1 history is hard-capped at ~67-69 days** (broker date floor 2026-07-06). **A literal
   6-month SCALP backtest is impossible on this feed** — SCALP's usable window is ~67 days.
   Reported as a limitation rather than substituted.
5. **`copy_rates_from_pos` caps at 50 000 bars**; beyond that MT5 returns `Invalid params`. A
   range query reaching past stored history *errors out* instead of truncating.

### Known unit defect preserved (not "fixed")

The arbiter's `expected_value` is carried in **DOLLARS** by the decision engine, but its grade
thresholds (`ev >= 0.40` / `ev >= 0.80`) read as **R-multiples**. With a median `ev` near $103 the
gate is vacuous — it never discriminates. The verification reproduces the comparison verbatim,
because the question is what the deployed logic selects, not what a corrected version would.

| SWING | 179d | 755 | **−0.0787** | −59.40 | 47.0 | 0.85 | 79.5 | **4/20** |

### RESULTS — prioritization (candidate-level, fixed `tp_r=1.5`, 438k candidates total)

| Mode | Candidates | Q5−Q1 R | Symbols agreeing | Top-1 vs rest | Inverse control |
|---|---|---|---|---|---|
| SWING | 46,583 | +0.0064 | 9/20 | +0.0432 | −0.1187 |
| DAY_TRADING | 182,358 | +0.0649 | **13/20** | **+0.0980** | −0.1277 |
| SCALP | 203,534 | −0.0035 | 9/20 | +0.0277 | −0.0756 |

Verdict: **only DAY_TRADING ranks correctly** (positive spread, majority of symbols agree, top-1
beats the rejected set). SWING and SCALP have a flat/non-monotonic utility gradient with coin-flip
symbol agreement, though their top-1 pick is still mildly positive and the inverse control is
always worse — so the ranking direction is right, it just carries very little information.

Notable: **the grade tiers above C are not ordered.** In all three modes GRADE A+ / A / B land
within noise of each other (e.g. SWING A+ −0.0385, A −0.0795, B −0.0338), while GRADE C is
consistently the worst (−0.20 to −0.24). The grades separate C from the rest but do not order the
rest. The `is_actionable` flag does help in every mode (SWING −0.038 vs −0.095, DAY −0.051 vs
−0.120, SCALP +0.153 vs +0.105).

### RESULTS — robustness re-analysis (`tools/prioritization_robustness.py`)

Stress-tested the verdicts rather than publishing the single-parameter version. Reads the saved
replay frames, so it costs no replay time.

- **Threshold sweep is decisive and it changes the story.** Raising the utility cut from 0.5 → 25
  (50×) moves expectancy by **≤ 0.02 R in every mode**. The entire step is at 0.0 → 0.5, which just
  drops the candidates the arbiter already scores 0. **The utility score is not usable as a
  continuous filter** — the binary `ev > 0 and directional` gate is what separates populations
  (~0.03–0.05 R).
- Top-k (1/2/3/5/10) and bucket count (3/4/5/10) both keep DAY_TRADING positive and SWING/SCALP
  ~zero or negative, so the mode verdicts are stable. SWING's bucket spread is sign-unstable
  (−0.029 / +0.007 / +0.007 / −0.048) — another reason not to call it a signal.
- **Per-symbol Spearman is positive in 14–18 of 20 symbols in every mode** (mean rho +0.046 to
  +0.079), while extreme-bucket agreement is only 9/20 for SWING/SCALP. So the signal is real but
  far too weak for an extreme-bucket test to detect and far too weak to trade.
- **In SWING, restricting to the actionable population flips the top-1 delta negative** (−0.006).
  The ranking can look mildly positive overall and be useless exactly where it is used. Always
  re-run the ranking test inside the population that actually trades.

### Bug found and fixed (surfaced by the test suite, not by me)

`tests/test_symbol_registry.py` had been *silently skipping* WTI: no broker manifest existed for
it, because `WTI` was unresolvable (`resolve_broker_symbol("WTI")` returned `"WTI"`, which the
broker does not list). My `WTI -> OILCash#` fallback made it resolvable, the manifest appeared, and
the parametrised registry-vs-broker test then caught a **pre-existing 10× error**:

| Field | Registry (was) | Broker (OILCash#) |
|---|---|---|
| `contract_size` | 1000.0 | **100.0** |
| `typical_spread_pips` | 3.0 | **13.0** |
| `asset_class` | COMMODITY | ENERGY (via `_CATEGORY`) |

Fixed all three in `jarvis/data/symbol_registry.py`, and added `"ENERGY": "COMMODITY"` to the
mismatch mapping in `registry_mismatches` (the registry's taxonomy is deliberately coarser and has
no ENERGY class). 281/281 registry tests pass after the fix.

**This changed WTI's backtest numbers**, because `typical_spread_pips` is the spread the backtest
charges (3 → 13 pips) and `contract_size` feeds the position sizer's minimum-lot check. WTI was
re-run across all three modes afterwards. Lesson: making a previously-unreachable symbol reachable
can expose latent spec errors — expect newly-enabled test cases to fail.
