## Engine integration of exit geometry — attempted then REVERTED (important)

Tried wiring the geometry into `BacktestEngine`. Rolled back with
`git checkout -- jarvis/backtesting/engine.py` (62 tests pass afterwards). Two defects:

1. **Runner hard cap negates the ladders.** Harness built B/C/D via
   `EXIT_GEOMETRIES(tp_r=1.0)` so the RUNNER got a 1.0R hard target → trades close the runner at
   1.0R BEFORE the 1.5R/2.5R rungs fire ⇒ B/C/D silently collapse to mode A. Ladder runners need
   `tp_r=None` (trail carries them), not 1.0.
2. **Mode A double-closes.** Mode A's schedule is a single 100% leg at tp_r; the new rung loop
   closes it AND the existing TP check closes it again → double-counted P&L. Only build rungs for
   schedules that contain a runner.

KEPT (additive, default to today's behaviour): `build_exit_geometry()` in
`jarvis/backtesting/exit_geometry.py`; `geometry_mode: str = "A_fixed_tp"` field on `WRTargetProfile`
(auto-serialised via `asdict`; `from_dict` filters to dataclass fields so old profiles load fine).

Remaining, in order: (1) build B/C/D with runner tp_r=None + rungs only when a runner exists;
(2) add an engine-vs-harness PARITY regression test (its absence is why both defects got through);
(3) persist geometry_mode through `calibrate_winrate.py`; (4) re-run `run_3month_backtest.py` and
confirm the engine reproduces the +0.1905R / PF 1.39 harness portfolio.

**Lesson: do not ship partially-wired execution changes to a safety-critical trading engine —

## DEFINITIVE answer to "why is it not profitable" (2026-09-12)

Measured on the reproducible engine backtest (`reports/backtest_3month_report.json`):

    avg_win_R = 0.2776   avg_loss_R = -1.0018   payoff = 0.2771
    breakeven WR = 1/(1+payoff) = 78.30%      achieved WR = 73.35%
    MARGIN = -4.95 win-rate points

**The system is ~5 win-rate points below breakeven on every symbol.** It is NOT an entry problem —
73% directional accuracy is genuine skill. It is an EXIT/PAYOFF problem: winners are banked at
~0.28R while losers run the full -1.00R.

Two mechanisms, both quantified:
1. The win-rate-chasing calibrator sets tiny tp_r (0.25-0.4), capping winners BY CONSTRUCTION.
2. Even where tp_r is larger, realised avg win is far BELOW tp_r — UK100 tp_r=1.0 realised 0.536R,
   USDJPY tp_r=0.6 realised ~0.18R — because breakeven lock + trail + time stops cut winners early.

Per-symbol margin (WR − breakeven WR): AUDUSD -2.67 · NAS100 -3.2 · NZDUSD -3.8 · XAUUSD -0.6 ·
UK100 +20 but exp -0.147 · USDJPY +3.5 but exp -0.253 (both: realised payoff far below tp_r).

**The 5.1 harness proved the fix:** with ladder/ATR-trail geometries and NO breakeven, the same
entries produce +0.1905R / PF 1.39 at only 45% WR. So profitability is gated on exit geometry,
not on entry quality and NOT on paper-vs-live mode (the -4.95 margin is pure arithmetic and is
identical in any execution mode).

### THE FINDING — the 75% win-rate objective is arithmetically self-defeating

`WR_breakeven = 1 / (1 + tp_r)` for a 1R stop. So **breaking even at 75% WR requires `tp_r ≥ 0.3333`**
(= 1/0.75 − 1). Below that, the geometry needs *more* than 75% just to break even, before costs.

- **7 of 16 symbols were calibrated to `tp_r < 0.3333`** (AUDUSD, BTCUSD, ETHUSD, EURUSD, NAS100,
  USDCHF, XAUUSD — all 0.25 or 0.30). **All 7 lose money out of sample (7/7).** Their mean in-sample
  WR is 76.5% — they *hit the target* — with mean in-sample expectancy already **negative (−0.0279)**.
- **8 symbols hit ≥75% in-sample WR; only 1 has positive OOS expectancy.** In-sample target-hitting
  is *anti-predictive*.
- **The 4 OOS-profitable symbols (GER40, SOLUSD, UK100, USDJPY) are exactly the 4 the report
  trades.** The gate and the arithmetic agree.

Mechanism: the cheapest way to raise WR is to shrink the target, so the search walks `tp_r` down —
into the region where 75% is unreachable at a profit. The objective defeats itself. Same pathology as
the BTCUSD `tp_r=0.25` → 78.5% WR → still loses money result, now shown to be systematic.

**Recommendation:** constrain `tp_r ≥ 1/target_wr − 1` (0.3333 at 75%; use ≥0.5 for a cost margin),
optimise **expectancy** and report WR as a consequence, and report `oos_target_met` only — the
in-sample flag is misleading.

## Exit-policy divergence fixed + grid-widening hypothesis REFUTED (21:00–21:20)

### Bug: engine and calibrator traded different exit schedules
`BacktestEngine` had `geom_trail = getattr(geom, "trail_atr", 1.5) or 1.5` — `None or 1.5` → **1.5**,
turning a *disabled* trail into a **live 1.5×ATR trail**. The simulator (`Geometry.to_policy`) and
`ExitGeometry.to_policy` both implement `trail_atr=None` as "trail off" by pushing
`trail_activation_r` to `1e9`. Every grid geometry has `trail_atr=None` and all 16 deployed profiles
are `A_fixed_tp` with `trail_atr: null`, so the engine was systematically trading a schedule the
calibrator never measured.

**Dormant below `tp_r = 2.0`** (the trail only engages at `trail_activation_r = 2.0`, which a 1.5R
trade never reaches) — which is exactly why the original author capped the grid at 1.5 after seeing
NAS100 diverge (calibrator predicted 44.2% WR/+0.125R, engine realised 23.3%/−0.246R).

Fixed by preserving None: `geom_trail = getattr(geom, "trail_atr", None)` and
`trail_atr=None if geom_trail is None else float(geom_trail)`. Added
`tests/test_winrate_targeting.py::test_engine_and_simulator_resolve_the_same_exit_policy`
(parametrised over None/1.5/2.0) + 5 more parity tests. ARCHITECTURE.md hard rule 10.

### Refuted: "widen the grid" (I proposed this — it was wrong)
Added `--wide-grid` (coarse grid 1.5 → 2.0/2.5) and re-ran at margin 0.17:

| config | trades | WR | total R |
|---|---:|---:|---:|
| margin 0.17, grid ≤ 1.5 | 908 | 53.8% | **−28.65** |
| margin 0.17, grid ≤ 2.5 | 757 | 49.3% | **−34.10** |
| **Δ** | −151 | −4.6pp | **−5.46R** |

**Worse on every aggregate measure** (6 symbols better, 8 worse, 2 unchanged).

**The lesson — a pile-up on a grid boundary does NOT mean the optimum is outside it.** The pile-up
just MOVED: narrow 10/16 pinned at 1.5 → wide 10/16 pinned at 2.5, same 10 symbols. So the pile-up
reflects an in-sample criterion **monotone in `tp_r`** (wider always looks better in-sample), not a
boundary effect. Same overfitting signature as the win-rate trap, mirrored: the WR objective pushed

## UI modernisation — unified design system (additive layer)

User asked to modernise the UI (layout, typography, colour, spacing), improve usability and
responsiveness/accessibility across screen sizes, **preserve existing functionality**, and
clarify scope + intended target users. Delivered as a **non-breaking additive layer** on top of
the four existing UIs rather than a rewrite of the four page sheets.

**New files**
- `jarvis/ui/static/css/hm_ui.css` (36.2 KB) — unified `--hm-*` token vocabulary, accessibility
  primitives, modernised shell components, toast system, consolidated breakpoints, print styles.
- `jarvis/ui/static/js/hm_ui.js` (24.9 KB) — toast API + `window.alert` shim, modal focus
  management, tab-strip ARIA + arrow keys, live region, active-nav marking, icon-button labelling.
- `docs/UI_DESIGN_SYSTEM.md` — scope, target-user personas, token migration map, trade-offs,
  verification evidence, findings, rollback.
- `docs/ui_preview.html` — standalone component gallery (opens the real stylesheet) for review.

**Integration:** all four templates got `hm_ui.css` after `auth.css`, `hm_ui.js` after the page
script, a skip link, `theme-color`/`color-scheme` metas, and cache-busters bumped
`?v=20260907_v1` -> `?v=20260912_v2`. Landmarks added: `<main>` already existed on index; added
`role="main" id="hm-main"` to `.screener-app-container` (stocks) and `.india-layout-container`
(india); **wrapped india_options' body-level sibling sections in `<main>`** (safe: that sheet has
no structural selectors and its JS does no DOM traversal). `role="tablist"`/`role="tab"`/
`aria-selected` added to all four mobile tab bars; `role="navigation"` on the nav wrappers.

**Key decisions**
- Legacy token aliasing as the migration path: re-point only names that were *identical* across
  pages (a no-op) or *defective*. Names whose values genuinely differ per page (`--bg-card`,
  `--bg-panel`, `--border-subtle`, `--bg-base`/`--bg-dark`/`--bg-main`) are **left alone**,
  because redefining them globally would silently repaint pages that are currently correct.
- `--text-dim` was the real defect: `#64748b` measured **3.89:1** on `--bg-surface` and **4.19:1**
  on `--bg-base` — below AA, and applied to 8-11px text. Replaced with `#8494ab` (**4.88:1**
  worst-case on the lightest surface in use).
- `--accent-cyan` unified (`#38bdf8` vs `#00d4ff` -> `#38bdf8`) — same semantic, two values.
- **No `@layer` for the overrides**: un-layered styles beat layered ones, so a layer would let the
  page CSS win. Load-last + equal specificity is the correct mechanism.
- **Small text: contrast over size.** Globally raising the 8-11px floor would overflow fixed-height
  grid rows holding 346 load-bearing ids, so only the contrast was fixed; the size ramp applies to
  new chrome.
- `!important` confined to 4 accessibility guards (focus ring, sr-only clip, reduced-motion,
  iOS input zoom) — 17 uses / 10 sites, documented in §4.2.
- Alert shim replaces `window.alert` so **the 10 call sites were not edited**; preserves message
  text/newlines/`undefined` return, and falls back to the native dialog if the toast path throws.

**Two restyles reverted after checking existing values** (would have shifted dense layouts for no
a11y gain): badge metrics (kept 10px/1.2/3px 8px instead of 11px/1.6) and HUD vertical padding
(terminal HUD is a fixed 56px box with zero vertical padding, stocks/india use 10px — a single
shared `padding-top` would have regressed one family, so they're handled separately with
`max()`/`calc()`). Intentional convergence: all four HUDs now carry `min-height: 56px`.

**Verification:** all four templates re-checked vs HEAD — **0 missing ids, 0 missing inline
onclick handlers, 0 missing classes** (206/71/265, 72/39/88, 65/42/128, 41/39/88); tag balance OK
on all 5 templates incl. `app.html`; CSS braces/parens balanced with **0 undefined custom
properties** (91 defined, 61 used); JS passes `node --check`. Server started on a test port and
`/static/css/hm_ui.css` + `/static/js/hm_ui.js` both served 200 with correct MIME types, and all
four pages served 200 with the new references present and **no stale `?v=20260907_v1`**.

**NOT verified: no visual browser regression pass** — browser automation is unavailable on Windows
in this environment. Structural/syntactic/contrast verification only; a human should open
`docs/ui_preview.html` then each page at desktop/tablet/phone widths before sign-off.

**Findings recorded (not acted on):**
- `app.html` + `app_shell.css` + `app_shell.js` are **orphaned** — no `/app` route and no generic
  template route in `jarvis/api/server.py`. Recommend deleting in a dedicated dead-code pass.
- Latent nav-convention divergence: `stocks.html` uses `btn-nav-active`, india/options use bare
  `active`, and each sheet styles only its own. Not a live bug (each page is self-consistent) but
  would break on consolidation. Resolved by styling **both** plus `aria-current="page"`, and by
  deriving the active state from the URL at runtime.
- The terminal's cross-page nav is present but buried in a dropdown — restyled as proper nav
  targets, no markup moved.

**Gotcha for future edits on this repo:** the file-write path intermittently fails with `EBUSY`
("resource busy or locked") *while still reporting success* — four edits silently did not persist.
Always re-grep to confirm a template edit actually landed; do not trust the success message alone.

Rollback is trivial: remove the two `<link>`/`<script>` references from the four templates — no
page stylesheet or page script was modified.
