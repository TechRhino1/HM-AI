Setting upstream tracking does **not** fix the hang. It only removes the need to name the remote and
branch. The selector is still in the chain, so a bare `git push` still stalls at rc=124 — the
bypass remains mandatory. This was added to the skill, along with the confirmed-working recipe and
the note that read operations (`ls-remote`, `fetch`) are unaffected.

# Session 2 — end-to-end audit, advanced terminal, regime-conditioned optimisation

Four-part request: audit every logic path, find interface/UI issues, redesign the UI on an advanced

## Regime-conditioned profit optimiser (new)

`jarvis/backtesting/regime_optimizer.py` + `tools/optimise_regime.py` + 34 tests.

The gap it closes: `optimizer.py` returns **one** geometry per trading mode, averaged over whatever
conditions the window contained. The win-rate calibrator (`intelligence/winrate_targeting.py`)
already had regime conditioning; the *profit* optimiser had none.

What made it cheap: `TradeOutcome` **already carries `regime`** (populated from the candidates
parquet, which carries a real `regime` column — 6 labels, not placeholders), and `select_sequential`
**already accepts a `regimes=` filter**. Both existed and were simply never used by the optimiser.
Conditioning is therefore free — `_outcomes` caches on the geometry alone, so one geometry scored
under six regimes costs one simulation plus cheap filtering passes.

Design points worth not relearning:

* **Selectivity must be regime-local.** `min_score` is a quantile of the symbol's own scores. The
  scores in COMPRESSION are not the scores in TREND_BULL, so resolving the quantile pooled and then
  filtering by regime silently rescales the selectivity. `SeriesBundle.min_score_for(q, regimes)`.
* **One blocking walk across regimes.** The engine holds one position per symbol whatever the
  regime. Selecting each regime independently books overlapping trades it can never take, and the
  phantom overlap clusters at regime turns — where the P&L is. Merge, then one `select_sequential`.
* **Order of decisions matters.** Search → deploy only on a measured win → *then* decide
  enable/disable from the geometry actually deployed. I got this backwards first and it disabled a
  regime whose own geometry was profitable, because the *pooled* geometry loses there.
* **`max_evaluations` is a budget per SEARCH.** It was an absolute counter, so with a low budget the
  first mode consumed it and later modes returned the unsearched seed geometry while reporting a full
  result. `tools/verify_ui_live.py` passes `max_evaluations: 12`, so it hit this on every run.
  Fixed with `_budget_start` / `_reset_budget()`.

**Measured result — all three modes (2026-09).** Two runs: SWING over all 20 symbols at
`--passes 3`, then all three modes over 8 liquid symbols at `--passes 1`. Smaller universe is less
converged but the direction is identical.

| Mode | Baseline OOS total R | Policy OOS total R | Trades | Verdict |
|---|---|---|---|---|
| SWING (20 sym) | −122.9 | −6.4 | 816 → 20 | improves total R |
| SWING (8 sym) | −12.9 | −1.6 | 342 → 105 | improves both |

The pooled optimum is not profitable in any mode. The policy's value is **loss avoidance, not

## Git lost its object store (incident #3)

Mid-session, `git diff --stat HEAD` returned **`fatal: bad revision 'HEAD'`**. Diagnosis, in order:

| Probe | Result |
|---|---|
| `.git/refs/` | **empty** — `refs/heads/main` gone |
| `git rev-parse HEAD` | `ambiguous argument 'HEAD'` |
| `git cat-file -t b62d547` | `could not get object info` |
| `.git/objects/pack/` | three **`.idx` files with no `.pack` files** |
| `.git/objects/` loose files | **0** |
| `.git/logs/HEAD` | **intact**, last entry `b62d547` |
| working tree | **intact** — `jarvis/` 131 files, 394 tracked |
| `git ls-remote origin` | `b62d547...` — remote had everything |

So the entire object database had been deleted while the working tree survived untouched. The
previous session's memory claimed "`.git/` survives these incidents" — **that is wrong**, and I
corrected it. The bundle in `.git/backup/` survived because it is a single file.

Recovery (worked first time):

```bash
cat .git/logs/HEAD | tail -5          # reflog survives; its last entry names your commit
git cat-file -t <sha>                 # confirm the object is really gone
git fetch origin                      # re-download objects; recreates origin/main
git update-ref refs/heads/main <sha>  # fetch does NOT restore a deleted local branch
git update-ref refs/remotes/origin/main <sha>
```

The trigger this time was a **`git stash push`** — the third incident and the third different
git ref/index-rewriting operation to precede one (twice `git rm`, now `git stash`). Conclusion
recorded in `MEMORY.md`: never `git stash` here. To compare old vs new behaviour, edit the file back
with the editor, run the test, edit it forward again — which is exactly how the recursion fix below
was validated. Fresh bundle written to `.git/backup/repo-20260915-0532.bundle`.

## The India endpoints were in unbounded mutual recursion, not slow

Three endpoints timed out at 240s (`/api/india/indices`, `/api/india/heatmap`,
`/api/stocks/screener`) and my first instinct was a slow provider. A **stack dump** — not the
symptom — is what identified it:

```
fetch_quotes -> get_india_profile -> DYNAMIC_HYDRATOR.get_profile
  -> hydrate_batch -> fetch_quotes -> ...        (repeating to the bottom of the stack)
```

`TradingViewDataProvider.fetch_quotes()` read its calibrated fallback price from
`get_india_profile()` / `get_stock_profile()`. Those **hydrate**, and hydration resolves quotes by
calling back into `fetch_quotes()` for the same symbol. Nothing raised, because `hydrate_batch` wraps
its `fetch_quotes` call in `except Exception` and **`RecursionError` is an `Exception`** — so each
level above swallowed it and unwound normally.

Measured: **233 re-entries** for a single NIFTY lookup, and the price that came back was the
last-resort **150.0** instead of NIFTY's own **24175.65**. So it was wrong data, not just a hang.

Fixed by reading `INDIA_UNIVERSE` / `STOCK_UNIVERSE` directly — the branch wants a baseline number,
which is what the static tables hold. After the fix NIFTY returns 24175.65 and the whole live
verifier run takes **37s** instead of timing out per route.

### Two testing lessons, both measured

1. **"Call it and expect no `RecursionError`" does not pin this bug.** That test passed against the
   *broken* code, because the exception is swallowed. Pin the **call**: patch the callee with a
   recorder that raises on entry and assert zero invocations.
2. **The re-entry test also passed against the broken code at first**, because a sibling test had
   warmed `_quote_cache` (15s TTL) and `fetch_quotes` returned from cache before reaching the
   fallback. Both caches are now cleared in `setUp`. A test that silently stops pinning anything is
   worse than no test.

`tests/test_provider_recursion.py` — 4 tests, **2 of them proven to fail against the pre-fix code**
(233 re-entries, `['NIFTY', 'NIFTY', ...]`). The source-level one parses with `ast` rather than
grepping, because the fix carries a comment naming the forbidden functions and a substring check
flagged that comment as a violation.

# Session 4 — the dashboard freeze, the account id, and the market links

## 1. The freeze on nav click — a self-retriggering MutationObserver

**Symptom.** Clicking *any* rail tab froze the page permanently. No error, no console message, no
failed request. It read like a crash, and it was reported as "freezing and crashing".

**Diagnosis, in the order that actually worked:**

1. A control run — load the page, **no clicks**, probe every second for 30s — stayed responsive
   (1–26ms). So the freeze was not a poll loop, and the click was genuinely the trigger. That single
   run halved the search space.
2. A CDP probe: `Debugger.enable`, click **without awaiting**, wait 5s, `Debugger.pause`. The pause
   **arrived**, with one frame: `sync @ :416:13`. A pause means JavaScript; no pause would have meant
   a native block (dialog or sync XHR).
3. `grep -n "function sync"` pointed at **`hm_ui.js:415`**.

**Root cause.** `enhanceTabGroup()` registered `new MutationObserver(sync)` watching
`attributeFilter: ['class', 'aria-selected']` on the tab group, and `sync()` wrote
`aria-selected` on those same tabs. **`setAttribute` queues a mutation record even when the value is
unchanged**, so every pass queued the next and the microtask queue never drained. Microtasks drain
before the browser may paint or dispatch input, so the block is permanent. It only fired on
interaction because the initial `sync()` ran *before* the observer was attached — `setView()` setting
`aria-selected` on `[data-view-btn]` was the first external write.

**Fix.** `setIfChanged()` — write only on a real change — plus a re-entrancy guard. A settled group
now produces no records at all, so the loop terminates after one pass. The observer is *kept*, and
the tool asserts it still works.

**Blast radius.** `hm_ui.js` is loaded by six templates (dashboard, console, index, india,
india_options, stocks), so all six carried the same freeze. Verified rather than assumed: all five
non-dashboard routes were loaded in a real browser and their tab groups clicked —
`/console` 6 tabs, `/classic` 5, `/india` 4, `/options` 5, `/stocks` 4 — every probe returned in
1–7ms with no block. Probe kept at `.scratch/probe_all_pages.js`.

## Session 7 — the target was not the problem either, and a real optimiser trap

The min_score sweep exposed something that generalises to **every** dimension of the search, not just
the quantile: `objective_value()` returns `-inf` for any geometry with expectancy ≤ 0, so once nothing
is profitable the descent's `score > best.score` test can never fire. It reports "no improvement" for a
dimension it *has* explored and found nothing on. `tp_r` was tried and never moved, and that told us
nothing. **A `NO FEASIBLE GEOMETRY` verdict with the seed as the best geometry is not evidence that a
dimension is useless** — pin it and measure it directly. Recorded as debt in ARCHITECTURE §12.

Swept `tp_r` 1.0 → 3.0 (seed otherwise, `max_evaluations=1`, both cost regimes, 30 runs, 14m17s).
Break-even win rate is `1/(1+tp)`: 50.0% at 1.0R, 40.0% at 1.5R, 25.0% at 3.0R.

**The finding is in the profit-factor column, not the expectancy column:**

| Style | PF across tp 1.0 → 3.0 |
|---|---|
| SWING | 0.878 – 0.903 |
| DAY_TRADING | 0.838 – 0.907 |
| SCALP | 0.678 – 0.706 |

**PF is essentially invariant to the target.** Widening it lowers the win rate almost exactly in
proportion, so the win-rate/loss-ratio trade-off is *proportional* rather than favourable, and PF never
crosses 1.0 in any mode. Stronger than "negative at every tp", and it is the mechanism.

It also resolves an apparent contradiction: SWING at tp=3.0 wins 25.34% against a 25.0% break-even yet
still loses 0.0757R/trade. The binary +tp/−1 model fails because `max_bars=200` times winners out
before they reach a distant target. Recovering the average win from PF
(`avg_win = PF × (1−w) / w = 0.898 × 0.7466 / 0.2534`) gives **2.65R, not 3.0R** — so a naive
break-even comparison at wide targets flatters the result and PF is the number to read.

**Important framing correction:** the project had already reached this verdict on 2026-09-12 —
`reports/entry_edge_verdict.md` and ARCHITECTURE §6 ("Known limitation: the entries carry no measured
edge"), from an attribution scan over 18,998 candidates plus a position-sizing test with significance
testing. Today's three experiments **independently reproduce and quantify** it from the optimiser's own
objective rather than from attribution; they are corroboration, not discovery. The one refinement:
that scan used quintiles, so it could not see the q=0.97/0.99 region where DAY_TRADING shows its
ordered-but-still-short trend. §6 now carries the corroboration and its numbers.

I had recommended the meta-label gate as "the only lever that can raise PF without a better

|---|---|---|---|

hydration call is, and everything else is a cache read.** Endpoint latency
