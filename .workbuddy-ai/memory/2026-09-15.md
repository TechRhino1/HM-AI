## The push hung, exactly as the skill predicts

`git push` on this machine does not fail — it **stalls silently**. The diagnostic signature matched
the `diagnose-git-push-auth` skill precisely:

| Probe | Result | Reading |
|---|---|---|
| `git ls-remote --heads origin` | exit 0 | Network fine; the problem is auth on the write path |
| `git config --get-all credential.helper` | `helper-selector`, then GCM | The known blocker is first in the chain |
| `git credential fill` | **exit 124 (hung)** | The selector is stuck — the decisive signal |

The fix from the skill worked on the first attempt, with no prompt and no user involvement:

```bash
GCM="C:/Users/Itrai/.workbuddy-ai/binaries/PortableGit/versions/1.2.0/mingw64/bin/git-credential-manager.exe"
timeout 180 git -c credential.helper= -c credential.helper="!$GCM" push origin main
```

`credential.helper=` (empty) resets the accumulated list so the effective chain becomes `[!GCM]` and
`helper-selector` never runs. **A plain `git push` had never once succeeded on this machine**; this
is the reliable path.

## Nuance worth remembering

Setting upstream tracking does **not** fix the hang. It only removes the need to name the remote and
branch. The selector is still in the chain, so a bare `git push` still stalls at rc=124 — the
bypass remains mandatory. This was added to the skill, along with the confirmed-working recipe and
the note that read operations (`ls-remote`, `fetch`) are unaffected.
