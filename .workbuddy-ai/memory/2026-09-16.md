### The blocker: six files deleted, then uncreatable

`git status` showed six unstaged deletions — `HM_dashboard.bat`, `HM_start.py`,

Every write path failed: `git checkout --` (rc 255, *unable to create file … Permission denied*),

**The diagnosis that mattered:** `os.stat` returned `FILE_NOT_FOUND` *while* Win32
`CreateFile(CREATE_ALWAYS)` returned `GetLastError=5` (ACCESS_DENIED). A deny ACE would let `stat`
succeed — so this was **delete-pending**: the name reserved by an open handle with delete-on-close.
`psutil` found no holder, but **181 of 301 processes raised AccessDenied**, so the holder (SYSTEM:
Defender/OneDrive) was invisible from user mode. Not worth chasing further.

**The recovery:** `os.link(alias, target)` creates the reserved directory entry where `CreateFile`
cannot, and because both names are one file object, writing through the writable alias fills the
blocked path. My first attempt failed with `LINK-FAILED … cannot find the file specified` — the bug
was mine: I deleted the alias before linking it, and **`os.link` needs the SOURCE to exist first**.
All six restored and SHA-1 verified against `git show :<path>`. `git diff` is empty (only
`core.autocrlf` normalisation), so the content is genuinely intact.

## Session 14 — dashboard layout redesign: hierarchy, space management, and the defect underneath

**Request:** reorganise and rearrange existing dashboard content into a clear logical hierarchy,
optimise screen space, improve grouping/spacing/alignment, keep it responsive.

### What was restructured (template)

Five monolithic panels each nested a second `.tt-panel__head` *inside* their `.tt-panel__body`, so a
sub-section was drawn with the same weight and band as a peer panel — the hierarchy read flat and the
eye had no entry point. Each became a real panel with its own head, body and grid slot:
Analytics Performance → `perf`+`reliab`+`hist`; News Next release → `next`+`detail`; Markets Global
equities → `equities`+`sector`; Analyst Quality gate → `gate`+`obj`; Backtest Progress →
`prog`+`results`+`jobs`. **18 `tt-slot--*` classes** now exist and `grid-template-areas` places them
by name, so placement is stated once instead of being inferred from DOM order and patched by
breakpoint overrides (which is how two `max-width` blocks came to disagree about a view's column
count). Every element id preserved — `verify_dashboard_render.js` 88/88 after each edit.

Also removed four inline `max-height: 32–46%` attributes. A percentage cap with no matching
`flex-grow` is the worst of both worlds: a dead band on a tall screen, a collapsed body on a short one.

### THE REAL DEFECT — `min-height` where `height` was meant

`.tt-app` declared `min-height: 100vh`. With an **indefinite** grid container height the `1fr` main
row resolves against **content**, so a view grew to its own height: **Trade measured 1263px tall on a
900px viewport.** The document scrolled, and every panel that was supposed to fill the screen was cut
off at the fold instead. Fix: `height: 100vh; height: 100dvh` + `overflow: hidden` on `.tt-main` +
`overflow-y: auto` on the active view (Trade opts out; its panes scroll internally). Result: view 734
≤ main 758, `docScrolls=false` at all four viewports. **This is the same family as the implicit `auto`
grid column** — a definite size that was never stated, silently resolved from content.

### Two more real defects the new checks found

* **A panel head can demand more width than the panel has, and `overflow: hidden` eats the surplus
  silently.** The Economic calendar head holds four controls plus a chip: **626px of min-content in a
  372px phone panel**, so the last select and the Refresh button were simply not drawn. Fixed with
  `height: auto; min-height: var(--tt-head-h); flex-wrap: wrap` on `.tt-panel__head` — `flex-wrap` is
  "wrap only if it does not fit", so a head with room is pixel-identical and no breakpoint is guessed.
* **Analytics gave the 8-column regime table a 1.35fr column while a half-empty panel sat beside it**,
  so the BASIS column scrolled sideways through a mid-word cut. The regime table now takes a
  full-width row beneath a 2x2 block of the short account panels: overview metrics above, dense detail
  below.

### Tooling

`tools/verify_ui_layout.js` grew three checks per view (154 → **238**): **document must not scroll**
(app shell), **view must fit inside main**, and **no silently clipped content**. The clip check
exempts `text-overflow: ellipsis` (designed truncation), `.tt-sr-only`, form controls, and
`#chart`/`#chart-tv` (lightweight-charts' own generated canvas) — a check that fires on those stops

## Session 15 — the broker-clock defect: MT5 times are not UTC

Picked up the last open backlog line ("Broker server time labelled as UTC (XM is GMT+2/+3) skews
session logic"). It was worse than the line suggested: it **disabled the stagnation exits.**

MT5 reports `position.time`, `deal.time` and `symbol_info_tick().time` as seconds on the **broker
server's** clock. `mt5_client.py:240` (`time.gmtime(p.time)`) and `database.py:201`
(`datetime.fromtimestamp(t, timezone.utc)`) each labelled those values UTC, putting them **2-3 hours
in the future**. `position_monitor._get_position_duration_sec` computes `now_utc - open_dt`, so the
holding time came out **2-3 hours short**, and `max(0.0, ...)` flattened it to a hard **zero for the
first three hours of every position's life**. The horizon-adaptive block is gated on
`if open_dur_sec > 0:`, so the whole time-decay section was skipped in exactly the window it exists
to police:

* SCALP "45 min without progress" could not fire until **3h45m**; DAY 6h fired at **9h**; SWING 36h
  at **39h**.
* `_determine_position_style` falls back to duration, so a **25-hour-old position read
  `DAY_TRADING` instead of `SWING`** — and style picks the exit rules and timeframe.

**Fix.** New `jarvis/data/broker_time.py`: derives the offset from the broker's own **freshest tick**
rather than hardcoding it (moves with the broker's DST, differs per broker — +5:30 India — and
survives a server change). Snapped to 1800s with a 300s tolerance plus a ±12/14h range check, so a
**weekend-stale tick is rejected** instead of producing a nonsense offset. Cached 600s (each
derivation is an MT5 round-trip per symbol). On failure returns 0 — the old behaviour — and **logs a
warning once**. `get_open_positions` and `sync_mt5_history` now stamp true UTC; the `max(0.0, …)`
clamp now warns instead of silently zeroing.

**The lesson worth keeping:** a silent clamp is a bug hider. `max(0.0, negative)` did not merely
produce a wrong number, it converted a loud sign error into a plausible zero that also happened to
satisfy the caller's `> 0` guard.

`tests/test_broker_time.py` — 13 tests; **3 fail on the pre-fix code**, including
`'DAY_TRADING' != 'SWING'`. Demonstrated by temporarily restoring the buggy line and re-running.

Verified: `pytest` **778 passed / 20 deselected** (was 765, +13); `audit_wiring.py` 133/133 modules
import, 0 broken refs, 0 import failures.

## Task #60/#61 — "no data" root-caused, and all six pages unified (`016c061`, pushed)

### #60 was NOT a server wedge — I retracted that claim

`.scratch/probe_no_data.js` (35s wait, past the 30s `provider` budget) over all six pages found exactly
**one** genuine defect: the console's watchlist stuck on `Loading…`. dashboard's six empty states are all
*correct* in UI-only mode (no broker, no orchestrator) — stocks/india/options/classic are clean.

The wedge theory died on measurement. `.scratch/sample_server.py` sampled the live server **while a page
sat on `Loading…`**: `/api/telemetry_state` returned **200 in 10–291 ms**, threads steady at **33**, no
`CLOSE_WAIT`, CPU normal. Two earlier candidates had already failed: a heavy backtest job (0 failures,
worst 400 ms over 110 s) and `TimeoutGuard` pool saturation (20 × 30s-hang behind a 0.1s timeout all
returned in ~0.1s). Also: **33 threads is the healthy baseline** — py-spy lists only 5 Python threads;
the other ~28 are BLAS natives it cannot unwind.

Real cause: **no page script sets a request timeout** — no `AbortController`, no `setTimeout` around a
fetch. So a request that never settles leaves the template's placeholder up forever, silently. Two
distinct failure modes, two fixes:
* `getJSON` *resolves* on transport failure, so the placeholder only clears if the render is
  **unconditional**. `renderWatchlist`'s seed was `if (syms.length)` → an empty radar (normal with no
  orchestrator) skipped the repaint entirely.
* A fetch that never settles resolves nothing → only a **watchdog** can repaint. Added
  `watchdogFirstPaint()` (12s): states the stall, marks the connection down, self-heals next poll.

`.scratch/probe_watchdog.js` — three phases (**hang / blocked / control**), 7/7. The first version
asserted "the watchdog message appears" and **failed for the right reason**: `getJSON` resolves on abort,
so the unguarded render covers that path and the watchdog only fires on a true hang. The invariant is
"the placeholder never persists", not "a specific message appears".

### Candle freshness — the "read-side dedup guard; candle freshness check" backlog item

`fetch_rates` stamped **every** frame `LIVE_MT5` and never checked its age, so a stalled feed was
indistinguishable from a live one and a decision taken on stale candles looks entirely valid.

Two traps, each with a test that pins it:

* **Bar opens are on the BROKER's clock**, like tick times — measured against raw UTC the age
  under-reports by the offset (2-3h for XM), so a stalled feed reads healthy. `classify_bar_freshness`
  takes the offset from the existing `broker_time` helper. The discriminating test asserts **both**
  branches (one frame FRESH at offset 0 and STALE at +3h), so dropping offset support fails the test
  instead of silently restoring the bug.
* **A weekend gap is not a stalled feed.** Forex/metals close ~21:00 UTC Fri, reopen ~21:00 UTC Sun, so
  a 40h-old H1 frame on a Saturday is expected → `MARKET_CLOSED`, not `STALE`. Otherwise the warning
  cries wolf every weekend and gets ignored.

Tolerance is **2.5 bar durations**, not 1: with `include_current_bar=False` the newest returned bar is
the last *closed* one and is already 1-2 durations old.

The verdict is stamped **once**, in the single candle entry point, and every decision path reads it via
`first_stale_frame` rather than re-deriving the age (a second age calc is a second thing to keep in step
with the broker's clock). **Both** decision paths are gated, because enforcing it in one and forgetting
the other is how the defect returns: `orchestrator.run_cycle_for_symbol` (refusal dict:
`decision=None`, `authorized=False`, `auth_reason` naming the role; `scan_all_modes` now skips None
decisions instead of handing them to the arbiter and logging an error for a handled condition) **and**
`server.py`'s auto-selection loop, which builds its decision directly and never went through the
orchestrator.

Only **STALE** blocks: UNKNOWN is a synthetic frame (already labelled and surfaced in the UI) and
MARKET_CLOSED is a shut market the session logic already governs — gating those would be a behaviour
change beyond the defect. Consequence: in UI-only mode every frame is SYNTHETIC (UNKNOWN), so the gate
never fires there and `verify_ui_live` still sees `decisions=1`.

Bar durations are **imported** from the provider's `TF_SECONDS_MAP` (added `M10`, which `TF_MAP` already
used) rather than copied — duplicating it is how a second source of truth starts.

`tests/test_candle_freshness.py` — **14 tests**; the offset test and the gate test both fail if their fix
is reverted. Full suite **816 passed / 20 deselected** (+14), no regressions.
