**Wrapping the brand descriptor in a `<span>` silently recoloured it at every
width**, because `hm_ui.css` has `.brand-text span { color: var(--hm-accent) }`.
Fixed at the source (`:not(.brand-text__desc)`), NOT by patching `color` back
in the new sheet — a patch would have masked a desktop regression behind a
sheet that only three pages load.

## pytest

`2871 passed + 133 errors = 3004` = the baseline count exactly. The 133 are
`ERROR at setup` from the **bulk-delete guard** on a reused `--basetemp`
(`_safe_shutil_rmtree`). Not a regression — a fixed basetemp accumulates >50
entries. Always a unique `--basetemp=.scratch/ptmp-$TS`.

**Correction, same day:** passing `--basetemp=.scratch/ptmp-$TS` at all made
pytest exit 0 with **zero output** — five attempts, including an escalated
run. Dropping the flag entirely (default temp dir) produced the real result:
`3004 passed, 1 skipped, 20 deselected, 2 warnings, 13 subtests passed in
247.85s`. So if a pytest run returns `RC=0` with an empty log, **suspect the
flag, not the suite** — re-run without `--basetemp` before concluding
anything. Also: `nohup … &` does not survive the turn here; run the suite in
the foreground (it needs ~4 min).

### Correction to the correction — the real cause is `env`, not `--basetemp`

That `--basetemp` diagnosis was **wrong**. Isolated properly today:

* `env FOO=bar python -c "print('env works')"` → **prints nothing**. The `env`
  command **silently swallows whatever it wraps** in this shell — no output, no
  error, exit 0. Any `env -u HTTP_PROXY … python -m pytest` therefore "runs"
  and reports success having done nothing at all.
* `python -m pytest …` also no-ops here (0 lines, exit 0). `pytest --version`
  works, which is what made this look like a suite problem.
* **Working invocation:** call pytest in-process and skip the wrapper —
  `NO_PROXY='*' <managed python> -c "import pytest,sys; sys.exit(pytest.main(['-q','--junit-xml=.scratch/pytest.xml']))"`.
  Note no proxy variables are set in this shell at all, so the `env -u …` dance
  was never needed. `HTTP_PROXY= HTTPS_PROXY= NO_PROXY='*' cmd` (shell-prefix
  assignment) also works if a variable ever does need overriding.
* Result this way: `3004 passed, 1 skipped, 20 deselected, 2 warnings, 13
  subtests passed in 211.46s`; junit XML `tests=3018 failures=0 errors=0
  skipped=1`. 3018 = 3004 passed + 13 subtests + 1 skipped.

**Rule: never wrap a command in `env` in this shell. If a command "succeeds"
instantly with no output, suspect the wrapper before the payload.**

## Mobile dock — the actual "UI is still broken" defect

The dock on `/stocks`, `/india`, `/options` is **server-rendered**, so its
buttons are tappable as soon as the HTML paints. The handler they call is
defined in the page controller (`stocks.js:1215`, `india.js:990`,
`india_options.js:840`), a blocking `<script>` ~360–540 lines of markup LATER.
An inline `onclick="switchMobileStocksView('screener')"` resolves that
identifier at **click time** in global scope, so any tap in that window threw
`switchMobileStocksView is not defined` and the dock did nothing.

It presented as an **intermittent** failure — a plain smoke test passed on a
warm cache and failed ~1 run in 3. `/console` and `/dashboard` were never
affected: they attach delegated listeners and have no inline `onclick`.

**Fix:** `jarvis/ui/static/js/mobile_dock.js` (new, loaded *before* the dock,
not deferred) installs the three entry points up front; each applies the
selected state immediately and hands the view to the controller via
`window.registerMobileView(key, fn)`, replaying a tap that arrived early. The
three controllers now register instead of assigning the global, with a
fallback assignment if the bootstrap is absent.

**Second defect, same family:** `state.activeMobileView` was **read** by the
resize handler and the init in all three files but **written only by
`india_options.js`**. So on stocks and india a resize at ≤900px, and the
`DOMContentLoaded` init, both fell back to the default and silently reverted
the user's tab. Each controller now records `state.activeMobileView = view`,
and the init calls `switchMobileXView(state.activeMobileView || <default>)`.

**New harness `tools/verify_mobile_dock.js`** (24 checks) reproduces the race
deterministically by intercepting and **holding** the controller script, then
tapping the dock. Verified non-vacuous: removing the bootstrap from
`stocks.html` turns **7 checks red** and reproduces the exact original
`switchMobileStocksView is not defined`. A warm-cache smoke test cannot see
this class of bug.

## Probe traps found today

* **`getComputedStyle` reports an animation on a `display:none` element.**
  A `querySelector('.dossier-card')` happily matched a **hidden bottom-sheet
  modal** and reported its `slideUpSheet` presentation animation as if it were
  the content card's entry motion. Filter by `getBoundingClientRect().width > 0`
  before believing a computed style. `slideUpSheet` on
  `.dossier-card`/`.modal-card` is *correct* (a sheet rises from the bottom) —
  do not "fix" it.
* **Templates are re-read per request** (no restart needed for `.html` edits),
  but a mutation and its restore landing **in the same second** served a stale
  render once — the restored file was correct on disk and in `curl` moments
  later, yet the test in that same command still saw the mutated page. Re-run
  before concluding a restore failed.
* `puppeteer-core` here has **no `waitUntil: 'commit'`**. To act on a page while
  a script is deliberately held, start `page.goto(...)` without awaiting and
  `waitForSelector` the element that precedes the held script.
